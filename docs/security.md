# Security model

Chrome Bridge is a trusted-local real-profile handoff bridge. The host policy, audit log, redaction, and confirmation-token flow are the security boundary for all raw TCP, CLI, and MCP clients.

## Trusted-local security warning

This bridge controls your real Chrome profile. It can read page content, take screenshots, drive forms, download files, inspect cookies through redacted probes, attach Chrome's debugger, and run script/debugger actions when policy allows them. Install it only for trusted local automation on a machine you control. Keep `bridge_token.txt`, `bridge_tokens.txt`, `extension_key.pem`, `bridge_policy.json`, debug logs, audit logs, and session trace artifacts (`bridge_traces/`) private and git-ignored.

The example policy is conservative: built-in defaults allow only `ping`, policy inspection, and lease actions until a local policy opts into more. Some README examples and live gates need explicit action/origin grants for the sites you intend to automate.

## Security notes

- TCP API is localhost-only and requires the shared token.
- Payload bodies such as cookies and DOM are not logged by the host.
- Host policy in `bridge_policy.json` (`BRIDGE_POLICY_FILE`) is the enforcement layer for every raw TCP/CLI/MCP client: the TCP API is localhost-only and token-gated, but token holders bypass MCP scoping, so deny/allow/confirmation rules are enforced in the native host before any action reaches the extension.
- MCP `readonly`/`allow_sensitive` controls are usability scoping, not the security boundary, because a client with the token can call the raw TCP API directly. Use `bridge_policy.json` for real restrictions; use `browser_policy_check` (or `test_client.py policyCheck`) to see what the host would decide.
- Built-in host defaults are fail-closed when no valid `bridge_policy.json` exists: only `ping`, `policyCheck`, `policyInfo`, and lease actions are allowed. `setup.sh` copies `bridge_policy.example.json` to make normal local automation an explicit opt-in. `policyInfo` is additionally answered host-side before the action gate (like `policyCheck`), so a client can always discover the active policy/audit file paths even under a deny-all policy; it returns only those paths, never policy contents.
- Actions listed in `requireConfirmation` return an opaque `confirmationToken` plus `resumeCommand`. `chrome-bridge confirm <token>` / MCP `browser_confirm` asks the host to recover the exact short-lived client identity, action, and payload; this intentionally allows an authenticated CLI client to approve a token produced by MCP. The older `browser_confirm_action` resend form remains available. Both paths re-run the original client's policy, live-origin, lease, and fingerprint checks before the host forwards anything, and tokens are one-use. Treat the opaque token as a short-lived local capability: this confirmation is friction against accidental use by a trusted token holder, not protection from a compromised bridge client or leaked token.
- Site policy (`allowedOrigins`/`deniedOrigins`) applies to tab-scoped actions too, not just URL-carrying ones. For an action whose payload has no URL/domain (e.g. `click`, `type`, `executeScript`, `getHTML` on a `tabId`), the host resolves that tab's live origin through a reserved internal lookup and evaluates policy against it before forwarding. When policy constrains origins and the origin cannot be resolved, the action is denied (fail-closed). `policyCheck` cannot see the live origin without forwarding, so its result includes `originDependent: true` for such actions to flag that the real request is additionally origin-checked.
- Python host only: set `BRIDGE_POLICY_APPROVAL_MODE=gui` (default on macOS) to show a native prompt when an otherwise-allowed action is blocked only because the target origin is not in `allowedOrigins`. The prompt offers `Deny`, `Allow This Time`, and `Always Allow`. `Allow This Time` creates a TTL-bound one-shot in-memory origin grant for the exact client/action/payload/target; `Always Allow` adds that origin to the local `bridge_policy.json`. Origin approval only authorizes the site, then the host re-runs normal policy evaluation, so actions in `requireConfirmation` still require a confirmation token. Set `BRIDGE_POLICY_APPROVAL_MODE=off` to disable prompts, or `BRIDGE_POLICY_APPROVAL_MODE=command` with `BRIDGE_POLICY_APPROVAL_COMMAND` for tests/custom frontends. Rust host users currently get the conservative deny/doctor flow without this GUI approval UX.
- GitHub attachment helpers (`githubAttachUploadedFiles`, `githubSubmitComment`, `githubAttachPrBody`) are narrow tab-scoped actions. They remain subject to host origin policy and reject any tab whose URL origin is not `https://github.com`; the PR-body helper additionally requires a `/owner/repo/pull/number` path and exact scoped editor/save controls. They do not require broad `executeScript*` allowlisting.
- Audit logs are JSONL at `BRIDGE_AUDIT_LOG_FILE` / `bridge_audit.jsonl`, one event per request with `ts`, `client`, `action`, `targets`, `decision`, `reason`, `requestId`. They intentionally omit payload and response bodies.
- Session trace artifacts are opt-in and local: set the policy key `traceDir` (default `null`) and both hosts append exactly one JSONL event per trace-eligible request to `<traceDir>/<traceId>.jsonl`, after the request is fully processed - allow, host denial, extension error, or timeout alike. An event carries `ts`, `client`, `action`, `decision`, `reason`, `requestId`, `durationMs`, `targets` (tab ids only, never URLs or titles), `traceId`, `responseHash`, an optional `snapshotHash`, and `success`. It never carries a payload body, a response body, or a token: content is represented only as a SHA-256 of the canonical redacted response, and secret masking is applied before hashing so a known credential cannot be a hash preimage. The trace id comes from the caller (`traceId`/`sessionId`/`taskSessionId`) or the response's `sessionId`, and the file name is sanitized to `[A-Za-z0-9._-]` and capped at 80 characters, so a caller-supplied id cannot escape `traceDir`. Traces are still sensitive browsing metadata - which sessions ran, which tabs, when, and what was denied - so keep `bridge_traces/` private and git-ignored, exactly like the audit log. Read them with `chrome-bridge trace summary|tail` or MCP `browser_trace_summary`/`browser_trace_tail`.
- Cookie and storage-state redaction is enabled by default through policy (`redact`): cookie values and sensitive storage keys are replaced with `<redacted>` before responses reach the client. Page-derived content from `getHTML`, `extractText`, `executeScript`, and `executeScriptCDP` is additionally masked against the client policy's `redactPatterns` (a list of regexes; use inline flags like `(?i)` for case-insensitivity) before it reaches the client.
- Secret masking is an additional, exact-match layer: set the policy key `secretMaskFile` to the path of a local `name=value` file (one pair per line, `#` comments allowed, mode `600` expected; see `bridge_secrets.txt.example`). Both hosts load it at policy load time, cache it by mtime, and replace every exact occurrence of each value with `<masked:name>` in every outbound response string (recursively, including nested objects and arrays) and in every audit-log field. Unlike `redactPatterns`, masking is independent of the `redact` toggle: these are known credentials and must never leave the host. A missing or unreadable file disables masking for that path after a single warning (logged and written to the audit log as `secret_mask_unavailable`). `bridge_secrets.txt` is gitignored; never commit real values.
- Request-level `"dryRun": true` (CLI `--dry-run`, MCP `browser_action` payload) makes the host evaluate a request - token, policy, lease, origin dependency, confirmation requirement - and answer `{success, dryRun, wouldForward, action, targets, verdict}` without forwarding anything to Chrome. It is deliberately side-effect free: it never acquires or resumes a lease, never mints or consumes a confirmation token, never triggers the origin-approval prompt, and never performs the internal live-origin lookup. Host-side actions (`lease`, `release`, `leaseStatus`, `policyCheck`, `policyInfo`, `confirm`) report `wouldForward: false` because they never reach Chrome. `policyCheck` additionally accepts `{"plan": [...]}` (max 50 steps) to preflight a whole plan in one host-side call.
- The Python and Rust native hosts enforce the same baseline policy, audit, and redaction rules; this parity is covered by the guardrails contract (`verify_guardrails_contract.py`). Python's optional origin-approval prompt is an extra UX layer that can persist a local policy grant before the baseline policy is re-evaluated.
- `executeScript` uses `chrome.scripting` in the page MAIN world and can be blocked by strict page CSP. `extractText`, `getHTML`, `waitForText`, and handoff body checks also use normal extension page access, so they do not open Chrome's debugger notice.
- `executeScriptCDP`, compact and full accessibility snapshots, browser interactions, selector waits, screenshots, viewport control, emulation, monitoring, interception, geolocation, and performance metrics use `chrome.debugger`. On task-owned tabs, nearby debugger-backed actions share one connection that closes after 30 idle seconds. Chrome's debugger notice is browser-wide; placing a tab in a group does not contain or hide it. Chrome 118 or newer is required so this idle timer remains reliable when the extension worker is inactive.
- `downloads`, `contentSettings`, `history`, `bookmarks`, `host_permissions: <all_urls>`, cookie access, debugger access, and script execution are powerful. Use this profile for trusted automation only.
- `sessionStatus` reports cookie names and counts only, never cookie values; `waitForHandoff` only focuses a tab, marks its task group as needing review, shows a compact card, and waits - neither reads, imports, nor overwrites cookies. Operating on the real profile is the bridge's design, not a leak, but `sessionStatus` output (which sites/accounts are logged in) is itself sensitive - keep it out of transcripts.
- Cookie and web-storage write ops (`setCookie`, `deleteCookie`, `setStorageItem`, `removeStorageItem`, `clearStorage`) are in the example policy's `requireConfirmation`, so each first call returns a one-use `confirmationToken` plus `resumeCommand` instead of mutating anything. They never log or echo the written value: the host omits payload bodies from the audit log, and the extension responses carry identifiers only - cookie name and domain for `setCookie`, the removed name for `deleteCookie`, scope and key for the storage item ops, and removed key counts for `clearStorage`. `deleteCookie` and `clearStorage` are destructive: they can sign the real profile out of a site or discard site state the human depends on.
- `searchHistory` and `searchBookmarks` read the real profile's private browsing record and are confirmation-gated in the example policy. `searchTabs` injects a bounded text match into every open `http`/`https` tab and returns origin hosts (never full URLs) plus capped snippets; snippets are page content, so treat all three outputs as sensitive and keep them out of transcripts. Tabs that cannot be scripted are skipped and only counted.
- `startScreencast` is confirmation-gated in the example policy because it begins **continuous** capture of a real, logged-in profile: for as long as it runs, every pixel the tab renders is buffered, which is a far larger exposure than a single `screenshot`. `screencastFrames` returns base64 image data and must be drained through `chrome-bridge screencastSave` / MCP `browser_screencast_save`, which write the frames to a local directory and return only counts, byte totals, and paths - never frame data. Frames buffer solely in the extension service worker (memory-only, so a worker restart ends the recording) with a hard bound of 600 frames or ~50MB, dropping and counting the oldest frames past either bound. `stopScreencast` discards whatever is still buffered.
- `consoleMessages` is raw-output-sensitive: console text and stack frames carry page data and script URLs. Its optional `resolveSourceMaps` mode (CLI `--source-maps`, MCP `browser_console_messages(resolve_source_maps=True)`) resolves generated frames to original build positions, and those `source` values can reveal a site's private source file names, directory layout, and developer paths - report resolved locations only when the user asked for them and keep them out of transcripts. Resolution reads a map only from the script's own origin or an inline `data:application/json` map and answers `sourceMapStatus: "crossOriginRefused"` otherwise, so no third-party origin is contacted. Script text and the map's `sourcesContent` are never retained or returned - the extension reads a script solely to find its `sourceMappingURL` comment - and the CLI additionally scrubs any source-text-shaped field before printing. Parsed maps stay in extension service-worker memory, capped at 100 per-tab entries and dropped when the tab closes. It is not a new action name, so existing `consoleMessages` policy entries govern the source-map mode too.
- The bridge still intentionally lacks Playwright-style isolated browser contexts/profiles and multi-browser support; it controls the real Chrome profile. That ambient real-profile session is the point: it is what lets an agent reuse your existing logins and hand off to you for steps it should not do itself.
- The MCP HTTP transport reads a per-request bridge token from `Authorization: Bearer` or `X-Bridge-Token` (see `docs/mcp.md`). Those headers are bearer credentials for your real Chrome profile: keep the listener on `127.0.0.1`, never put it behind a shared or public reverse proxy, and never paste the header value into transcripts or logs. A request with no token header runs under the server's ambient `bridge_token.txt` identity, so an unauthenticated local caller reaching the endpoint gets that identity's policy scope - the port binding is the boundary.
- Private extension keys and store credentials must stay out of git. `extension_key.pem` (and any privately-held CRX packing key) is a local identity secret: it is git-ignored, it is never packaged, and `scripts/package_extension_store.py` neither creates nor reads it - the store upload zip contains only `manifest.json`, `background.js`, `wake.html`, and `wake.js`, and the script refuses to write a manifest carrying a `key` field. Store dashboard assets and metadata (publisher account details, screenshots of a logged-in real profile, review notes, OAuth client secrets or refresh tokens for any store API) are equally out of scope for this repository: no packaging path here uploads anything or contacts a Chrome Web Store API, so uploads stay a manual, human-performed step.

## Handoff telemetry blackout

While a `waitForHandoff` request is in flight through a native host, a human is typing a password, a 2FA code, or a payment detail into the real tab. For that whole window the host **denies observation actions before policy evaluation**, so no client can watch the handoff:

- Blacked-out actions: `screenshot`, `extractText`, `getHTML`, `storageState`, `printToPDF`, `searchTabs`, `getCurrentState`, and `screencastFrames` (draining buffered screencast pixels is the same exposure class as a screenshot; the `startScreencast`/`stopScreencast` control verbs are not blocked). They are answered `{"success": false, "error": "handoff in progress", "blackout": true}` and audited with decision `handoff_blackout`. Nothing is forwarded to Chrome.
- The blackout applies to **every** client, including the one that started the handoff, and it outranks policy: an `allowedActions: ["*"]` policy does not lift it.
- Everything else passes normally: `ping`, `policyCheck`, `policyInfo`, lease verbs, the `waitFor*` family, and interaction actions are unaffected.
- Scope is per tab when the handoff payload carries a numeric `tabId`. **A handoff with no `tabId` is global**: the extension resolves the active tab, which the host cannot see, so the safer reading is that every tab is blacked out. Symmetrically, an observation request that omits `tabId` is denied by any live handoff, since it could land on the tab the human is using.
- The in-flight record is registered immediately before the forward and released on every exit path - normal response, extension error, or timeout - so a failed handoff can never leave a host permanently blind. Both hosts serve each TCP connection on its own thread, so the registry is shared state guarded by a mutex and covers concurrent client connections (a handoff on one connection blacks out observation on all others).
- A `dryRun` request for a blacked-out action reports `wouldForward: false` with `verdict.reason: "handoff in progress"` and `verdict.blackout: true`.
