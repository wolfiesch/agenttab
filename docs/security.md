# Security model

Chrome Bridge is a trusted-local real-profile handoff bridge. The host policy, audit log, redaction, and confirmation-token flow are the security boundary for all raw TCP, CLI, and MCP clients.

## Trusted-local security warning

This bridge controls your real Chrome profile. It can read page content, take screenshots, drive forms, download files, inspect cookies through redacted probes, attach Chrome's debugger, and run script/debugger actions when policy allows them. Install it only for trusted local automation on a machine you control. Keep `bridge_token.txt`, `bridge_tokens.txt`, `extension_key.pem`, `bridge_policy.json`, debug logs, audit logs, session trace artifacts (`bridge_traces/`), recorded workflows (`bridge_workflow_last.json` and any workflow file you save), and the selector cache (`bridge_action_cache.json`) private and git-ignored.

The example policy is conservative: built-in defaults allow only `ping`, policy inspection, and lease actions until a local policy opts into more. Some README examples and live gates need explicit action/origin grants for the sites you intend to automate.

## Security notes

- TCP API is localhost-only and requires the shared token.
- Payload bodies such as cookies and DOM are not logged by the host.
- Host policy in `bridge_policy.json` (`BRIDGE_POLICY_FILE`) is the enforcement layer for every raw TCP/CLI/MCP client: the TCP API is localhost-only and token-gated, but token holders bypass MCP scoping, so deny/allow/confirmation rules are enforced in the native host before any action reaches the extension.
- MCP `readonly`/`allow_sensitive` controls are usability scoping, not the security boundary, because a client with the token can call the raw TCP API directly. Use `bridge_policy.json` for real restrictions; use `browser_policy_check` (or `test_client.py policyCheck`) to see what the host would decide.
- Built-in host defaults are fail-closed when no valid `bridge_policy.json` exists: only `ping`, `policyCheck`, `policyInfo`, and lease actions are allowed. `setup.sh` copies `bridge_policy.example.json` to make normal local automation an explicit opt-in. `policyInfo` is additionally answered host-side before the action gate (like `policyCheck`), so a client can always discover the active policy/audit file paths even under a deny-all policy; it returns only those paths, never policy contents.
- Actions listed in `requireConfirmation` return an opaque `confirmationToken` plus `resumeCommand`. `chrome-bridge confirm <token>` / MCP `browser_confirm` asks the host to recover the exact short-lived client identity, action, and payload; this intentionally allows an authenticated CLI client to approve a token produced by MCP. The older `browser_confirm_action` resend form remains available. Both paths re-run the original client's policy, live-origin, lease, and fingerprint checks before the host forwards anything, and tokens are one-use. Treat the opaque token as a short-lived local capability: this confirmation is friction against accidental use by a trusted token holder, not protection from a compromised bridge client or leaked token.
- Site policy (`allowedOrigins`/`deniedOrigins`) applies to tab-scoped actions too, not just URL-carrying ones. For an action whose payload has no URL/domain (e.g. `click`, `type`, `executeScript`, `getHTML` on a `tabId`), the host resolves that tab's live origin through a reserved internal lookup and evaluates policy against it before forwarding. When policy constrains origins and the origin cannot be resolved, the action is denied (fail-closed). `policyCheck` cannot see the live origin without forwarding, so its result includes `originDependent: true` for such actions to flag that the real request is additionally origin-checked.
- Python host only: set `BRIDGE_POLICY_APPROVAL_MODE=gui` (default on macOS) to show a native prompt when an otherwise-allowed action is blocked only because the target origin is not in `allowedOrigins`. The prompt offers `Deny`, `Allow This Time`, and `Always Allow`. `Allow This Time` creates a TTL-bound one-shot in-memory origin grant for the exact client/action/payload/target; `Always Allow` adds that origin to the local `bridge_policy.json`. Origin approval only authorizes the site, then the host re-runs normal policy evaluation, so actions in `requireConfirmation` still require a confirmation token. Set `BRIDGE_POLICY_APPROVAL_MODE=off` to disable prompts, or `BRIDGE_POLICY_APPROVAL_MODE=command` with `BRIDGE_POLICY_APPROVAL_COMMAND` for tests/custom frontends. Rust host users currently get the conservative deny/doctor flow without this GUI approval UX.
- Per-site permission modes (`siteModes`) attach a mode to an origin pattern instead of an action: `manual`, `auto` (the default when no pattern matches), or `skip`. They are merged **per pattern** across the `default` and `clients.<name>` layers, so a client layer overriding one origin inherits every other origin's mode. A mode only moves the confirmation gate, never the action or origin gates: a `deniedActions` or `deniedOrigins` match still denies, and `skip` only relaxes actions the policy already allows. `manual` requires a confirmation token for every mutating or high-risk action on a matching origin even when nothing is listed in `requireConfirmation`. `skip` pre-approves the confirmation gate for a matching origin, so no token is minted at all - and the waiver is written to the audit log as decision `confirmation_waived` with reason `siteMode skip`, because under an unattended pre-approval that log entry is the only trace a human later sees. When two patterns match, the longest pattern wins (a length tie is broken by the lexicographically smaller pattern) in both hosts, and a value outside `manual|auto|skip` is ignored rather than guessed at. `policyCheck`, `policyCheck --plan`, and every `dryRun` verdict report the resolved `siteMode` (null when no origin is known yet or no pattern matches). Edit modes with `chrome-bridge policy site-mode <originPattern> manual|auto|skip [client]` and `chrome-bridge policy clear-site-mode <originPattern> [client]`; MCP deliberately exposes no policy-mutation tool.
- `skip` can **never** waive these non-skippable confirmations, in either host: `executeScript`, `executeScriptCDP`, `getCookies`, `storageState`, `setCookie`, `deleteCookie`, `setStorageItem`, `removeStorageItem`, `clearStorage`, `startScreencast`, `clickAt`. They execute arbitrary script, read or rewrite real profile credentials and storage, start continuous capture of a logged-in profile, or click with no auditable element identity. An origin-level pre-approval is a statement about a *site*, not about those capabilities, so they keep requiring a per-call token no matter what `siteModes` says.
- GitHub attachment helpers (`githubAttachUploadedFiles`, `githubSubmitComment`, `githubAttachPrBody`) are narrow tab-scoped actions. They remain subject to host origin policy and reject any tab whose URL origin is not `https://github.com`; the PR-body helper additionally requires a `/owner/repo/pull/number` path and exact scoped editor/save controls. They do not require broad `executeScript*` allowlisting.
- Audit logs are JSONL at `BRIDGE_AUDIT_LOG_FILE` / `bridge_audit.jsonl`, one event per request with `ts`, `client`, `action`, `targets`, `decision`, `reason`, `requestId`. They intentionally omit payload and response bodies.
- Session trace artifacts are opt-in and local: set the policy key `traceDir` (default `null`) and both hosts append exactly one JSONL event per trace-eligible request to `<traceDir>/<traceId>.jsonl`, after the request is fully processed - allow, host denial, extension error, or timeout alike. An event carries `ts`, `client`, `action`, `decision`, `reason`, `requestId`, `durationMs`, `targets` (tab ids only, never URLs or titles), `traceId`, `responseHash`, an optional `snapshotHash`, and `success`. It never carries a payload body, a response body, or a token: content is represented only as a SHA-256 of the canonical redacted response, and secret masking is applied before hashing so a known credential cannot be a hash preimage. The trace id comes from the caller (`traceId`/`sessionId`/`taskSessionId`) or the response's `sessionId`, and the file name is sanitized to `[A-Za-z0-9._-]` and capped at 80 characters, so a caller-supplied id cannot escape `traceDir`. Traces are still sensitive browsing metadata - which sessions ran, which tabs, when, and what was denied - so keep `bridge_traces/` private and git-ignored, exactly like the audit log. Read them with `chrome-bridge trace summary|tail` or MCP `browser_trace_summary`/`browser_trace_tail`.
- Cookie and storage-state redaction is enabled by default through policy (`redact`): cookie values and sensitive storage keys are replaced with `<redacted>` before responses reach the client. Page-derived content from `getHTML`, `extractText`, `executeScript`, and `executeScriptCDP` is additionally masked against the client policy's `redactPatterns` (a list of regexes; use inline flags like `(?i)` for case-insensitivity) before it reaches the client.
- Secret masking is an additional, exact-match layer: set the policy key `secretMaskFile` to the path of a local `name=value` file (one pair per line, `#` comments allowed, mode `600` expected; see `bridge_secrets.txt.example`). Both hosts load it at policy load time, cache it by mtime, and replace every exact occurrence of each value with `<masked:name>` in every outbound response string (recursively, including nested objects and arrays) and in every audit-log field. Unlike `redactPatterns`, masking is independent of the `redact` toggle: these are known credentials and must never leave the host. A missing or unreadable file disables masking for that path after a single warning (logged and written to the audit log as `secret_mask_unavailable`). `bridge_secrets.txt` is gitignored; never commit real values.
- Request-level `"dryRun": true` (CLI `--dry-run`, MCP `browser_action` payload) makes the host evaluate a request - token, policy, lease, origin dependency, confirmation requirement - and answer `{success, dryRun, wouldForward, action, targets, verdict}` without forwarding anything to Chrome. It is deliberately side-effect free: it never acquires or resumes a lease, never mints or consumes a confirmation token, never triggers the origin-approval prompt, and never performs the internal live-origin lookup. Host-side actions (`lease`, `release`, `leaseStatus`, `policyCheck`, `policyInfo`, `confirm`) report `wouldForward: false` because they never reach Chrome. `policyCheck` additionally accepts `{"plan": [...]}` (max 50 steps) to preflight a whole plan in one host-side call.
- The Python and Rust native hosts enforce the same baseline policy, audit, and redaction rules; this parity is covered by the guardrails contract (`verify_guardrails_contract.py`). Python's optional origin-approval prompt is an extra UX layer that can persist a local policy grant before the baseline policy is re-evaluated.
- `executeScript` uses `chrome.scripting` in the page MAIN world and can be blocked by strict page CSP. `extractText`, `getHTML`, `waitForText`, and handoff body checks also use normal extension page access, so they do not open Chrome's debugger notice.
- `executeScriptCDP`, compact and full accessibility snapshots, browser interactions, selector waits, screenshots, viewport control, emulation, monitoring, interception, geolocation, and performance metrics use `chrome.debugger`. On task-owned tabs, nearby debugger-backed actions share one connection that closes after 30 idle seconds. Chrome's debugger notice is browser-wide; placing a tab in a group does not contain or hide it. Chrome 118 or newer is required so this idle timer remains reliable when the extension worker is inactive.
- `downloads`, `contentSettings`, `history`, `bookmarks`, `host_permissions: <all_urls>`, cookie access, debugger access, and script execution are powerful. Use this profile for trusted automation only.
- `sessionStatus` reports cookie names and counts only, never cookie values; `waitForHandoff` only focuses a tab, marks its task group as needing review, shows a compact card, and waits - neither reads, imports, nor overwrites cookies. Operating on the real profile is the bridge's design, not a leak, but `sessionStatus` output (which sites/accounts are logged in) is itself sensitive - keep it out of transcripts.
- Cookie and web-storage write ops (`setCookie`, `deleteCookie`, `setStorageItem`, `removeStorageItem`, `clearStorage`) are in the example policy's `requireConfirmation`, so each first call returns a one-use `confirmationToken` plus `resumeCommand` instead of mutating anything. They never log or echo the written value: the host omits payload bodies from the audit log, and the extension responses carry identifiers only - cookie name and domain for `setCookie`, the removed name for `deleteCookie`, scope and key for the storage item ops, and removed key counts for `clearStorage`. `deleteCookie` and `clearStorage` are destructive: they can sign the real profile out of a site or discard site state the human depends on.
- `searchHistory` and `searchBookmarks` read the real profile's private browsing record and are confirmation-gated in the example policy. `searchTabs` injects a bounded text match into every open `http`/`https` tab and returns origin hosts (never full URLs) plus capped snippets; snippets are page content, so treat all three outputs as sensitive and keep them out of transcripts. Because a single `searchTabs` call can return content from tabs the agent was never pointed at, MCP gates `browser_search_tabs` behind `BRIDGE_MCP_ALLOW_SENSITIVE=1` alongside history and bookmarks. Tabs that cannot be scripted are skipped and only counted.
- `startScreencast` is confirmation-gated in the example policy because it begins **continuous** capture of a real, logged-in profile: for as long as it runs, every pixel the tab renders is buffered, which is a far larger exposure than a single `screenshot`. `screencastFrames` returns base64 image data and must be drained through `chrome-bridge screencastSave` / MCP `browser_screencast_save`, which write the frames to a local directory and return only counts, byte totals, and paths - never frame data. Draining is irrecoverable, so both saves create and validate the destination *before* consuming the buffer, and clear only a prior save's artifacts (`frame-*.png`, `frame-*.jpg`, `frames.json`, `screencast.mp4`) from it so a shorter later save cannot silently present an earlier recording's frames as its own. Because the save consumes the buffer and writes local files, MCP classifies `browser_screencast_save` as mutating, not read-only, and drops it under `BRIDGE_MCP_READONLY=1`. Frames buffer solely in the extension service worker (memory-only, so a worker restart ends the recording) with a hard bound of 600 frames or ~50MB, dropping and counting the oldest frames past either bound. `stopScreencast` discards whatever is still buffered.
- `consoleMessages` is raw-output-sensitive: console text and stack frames carry page data and script URLs. Its optional `resolveSourceMaps` mode (CLI `--source-maps`, MCP `browser_console_messages(resolve_source_maps=True)`) resolves generated frames to original build positions, and those `source` values can reveal a site's private source file names, directory layout, and developer paths - report resolved locations only when the user asked for them and keep them out of transcripts. Resolution reads a map only from the script's own origin or an inline `data:application/json` map and answers `sourceMapStatus: "crossOriginRefused"` otherwise, so no third-party origin is contacted. Script text and the map's `sourcesContent` are never retained or returned - the extension reads a script solely to find its `sourceMappingURL` comment - and the CLI additionally scrubs any source-text-shaped field before printing. Parsed maps stay in extension service-worker memory, capped at 100 per-tab entries and dropped when the tab closes. It is not a new action name, so existing `consoleMessages` policy entries govern the source-map mode too.
- The bridge still intentionally lacks Playwright-style isolated browser contexts/profiles and multi-browser support; it controls the real Chrome profile. That ambient real-profile session is the point: it is what lets an agent reuse your existing logins and hand off to you for steps it should not do itself.
- The MCP HTTP transport reads a per-request bridge token from `Authorization: Bearer` or `X-Bridge-Token` (see `docs/mcp.md`). Those headers are bearer credentials for your real Chrome profile: keep the listener on `127.0.0.1`, never put it behind a shared or public reverse proxy, and never paste the header value into transcripts or logs. A request with no token header runs under the server's ambient `bridge_token.txt` identity, so an unauthenticated local caller reaching the endpoint gets that identity's policy scope - the port binding is the boundary.
- Private extension keys and store credentials must stay out of git. `extension_key.pem` (and any privately-held CRX packing key) is a local identity secret: it is git-ignored, it is never packaged, and `scripts/package_extension_store.py` neither creates nor reads it - the store upload zip contains only `manifest.json`, `background.js`, `wake.html`, and `wake.js`, and the script refuses to write a manifest carrying a `key` field. Store dashboard assets and metadata (publisher account details, screenshots of a logged-in real profile, review notes, OAuth client secrets or refresh tokens for any store API) are equally out of scope for this repository: no packaging path here uploads anything or contacts a Chrome Web Store API, so uploads stay a manual, human-performed step.
- Page content is untrusted input, not instruction. `extractStructured` narrows what a page can hand back to the fields a JSON Schema subset describes and never returns raw page text; `scanPromptInjection` reports a bounded heuristic `risk`/`matches` view of instruction-like page text (snippets capped at 160 characters, full text never returned), and `extractText`/`getHTML` can carry the same block as opt-in `injectionScan` metadata. Both are read-only observation actions and neither is a permission decision - see "Untrusted page content and prompt-injection posture" below.
- **A recorded workflow can reproduce mutating actions.** `startWorkflowRecording` and `replayWorkflow` are confirmation-gated in the example policy. Recording observes only what the bridge itself dispatched - never human clicks or keystrokes - so it can never capture more than the recording client was already allowed to do, and a failed action is never recorded. Replay is not a bypass: **before the outer `replayWorkflow` request is forwarded at all**, both native hosts walk `workflow.steps[]` - applying the same `tabId` retargeting the extension will apply, so a caller-supplied `tabId` is what gets origin-checked - and run each step through the full action, origin, `siteModes`, lease, and blackout pipeline. Any denied step denies the whole replay as `policy denied: workflow step <n>: <reason>`, and a reserved host-internal action is never dispatchable as a step. There is **no aggregate confirmation token**: a nested step that still requires confirmation after its own `siteModes` is applied fails the replay with `policy denied: workflow step <n> requires confirmation` and mints no token, because one outer approval cannot stand in for per-step approval and a half-run workflow has already mutated the page. Grant such a step explicitly through policy or a `skip` site mode instead. The extension then additionally refuses a step per step when the live tab origin is not in the workflow's `policy.requiredOrigins`. The exposure is the file: `bridge_workflow_last.json` and any `--out` path hold a replayable sequence of real mutations against a logged-in profile. They are git-ignored and written mode `600`; review a workflow before replaying one you did not record.
- Typed and stored values are redacted out of recordings by default. `type`/`fill` text, `setCookie`/`setStorageItem` values, `handleDialog` prompt text, and any credential-shaped payload key (`token`, `password`, `secret`, `credential`, `authorization`, `api_key`) are recorded as `<redacted>` with `requiresValue: true` and a `bindingKeys` entry, so a macro of a login never carries the password. Replay refuses the **entire** workflow - before running any step - until every redacted field is supplied through `bindings`/`--binding step<N>.<field>=<value>`, which keeps the secret in the caller's hands rather than on disk and prevents a partially-applied macro that stops at the credential field. `recordSensitive: true` (CLI `--record-sensitive`) opts one recording or one call out of that redaction and writes the literal value into the workflow file; use it only when you accept that file as a secret.
- The semantic-selector cache only self-heals **semantic** selectors (`text=`, `label=`, `role=`, `aria=`). A CSS selector is a literal address and is never cached or retargeted, so a stale CSS step fails instead of silently acting on a different element. A cached entry maps `(origin+pathname, semantic selector)` to a CSS path that resolved once, and a hit is trusted only when that path and the original semantic selector resolve to the **same live DOM node**: a path that still resolves but now addresses a replacement element is discarded just like one that stopped resolving, the semantic selector is re-resolved, and the step reports `selfHealed: true`. That closes the case where a page swaps a control and the old path keeps matching something - "still resolves" is not "still the right element". Entries imported from a cache file are rejected unless their selector is semantic and go through the same identity check at resolution time, so an edited `bridge_action_cache.json` cannot redirect a step onto a substituted element. The file is git-ignored and mode `600`: it holds no page content, but it does map a site's DOM structure.

## Untrusted page content and prompt-injection posture

Everything the bridge reads out of a page - `extractText`, `getHTML`, `extractStructured`, `observe`, `searchTabs`, console text, intercepted bodies - is **data authored by whoever controls that page**. It is never instruction for the agent driving the browser, even when it is written as one, and even when it names the agent, its tools, or its operator.

- `scanPromptInjection` (CLI `chrome-bridge scanPromptInjection`, MCP `browser_scan_prompt_injection`, or `scanPromptInjection: true` on `extractText`/`getHTML`) flags instruction-like text by kind: instruction override, system-prompt disclosure, credential exfiltration, shell execution, policy tampering, operator concealment, permission coercion, tool redirection, and URL-borne data exfiltration. It returns `risk` (`low`/`medium`/`high`), `matches` with `kind`, `severity`, and a snippet capped at 160 characters, and `scannedChars`.
- The scanner is **heuristic** and deliberately small. It has false positives (a support page legitimately telling a human to click Allow) and false negatives (obfuscated, translated, encoded, or image-borne instructions). `risk: low` is not a clean bill of health.
- A scan result is **never an authorization decision**. It grants nothing and denies nothing: policy `allowedActions`/`deniedActions`, `requireConfirmation` gates, the origin allowlist, the cooperative lease, and the handoff blackout remain the only enforcement surface, and no risk value changes any of them. Do not read `risk: low` as permission to proceed, or `risk: high` as a substitute for a policy denial.
- `extractStructured` reduces exposure - only schema-described values cross the boundary, and the page text the extension read to find them stays in the extension - but those values are still page-authored. A `string` field can carry an injection attempt; schema validation constrains shape and type, not intent.
- Report page-derived findings as evidence, never execute them. A confirmation-gated action is confirmed by the human through `chrome-bridge confirm <token>`, never by text discovered on a page.

## Scheduled workflows and the no-human-present trust model

`chrome-bridge schedule workflow <workflowPath> --at <ISO8601>|--interval <seconds> [--name <name>]` writes **local metadata only**, into git-ignored `bridge_schedules.json` (mode `600`, or `BRIDGE_SCHEDULE_FILE`). Understand precisely what it is not:

- **It starts nothing.** Chrome Bridge ships no scheduler daemon, no timer thread, and no wake-up path for scheduled work. Registering a schedule does not make a workflow run - not once, not later, not in the background. Something outside the bridge (cron, launchd, systemd timers, a CI job, or a human) has to invoke the printed `runCommand`, and until it does, the entry is inert text on disk.
- **The registry is metadata, not a workflow.** An entry records the schedule name, the absolute workflow path, the trigger, the step count, the workflow's declared `policy.requiredOrigins`, the registration timestamp, and the run command. Step payloads are validated and then never copied into it, because a recorded step can carry typed text, search terms, or form values.
- **Registration is not authorization.** The host evaluates every replayed step at run time against the policy in force at that moment - `allowedActions`, `deniedActions`, the origin lists, `requireConfirmation`, `siteModes`, the lease, and the handoff blackout. A schedule cannot pre-authorize anything, and a workflow whose origins are not granted simply fails, one step at a time, in the audit log.
- **Unattended means no one is there to confirm.** A confirmation-gated step run with no human present blocks on a token nobody will approve, so an unattended workflow needs its origins explicitly granted and, where you accept the tradeoff, `siteModes: {"<origin>": "skip"}` for the specific site. That is a deliberate, auditable decision: `skip` still cannot waive the non-skippable set above, so no schedule can silently execute script, read cookies or storage state, write or delete cookies or web storage, start a screencast, or click by coordinate.
- **Prefer `manual` for anything you would not want to discover after the fact.** An origin left at `auto` with an empty `requireConfirmation` and a periodic trigger is the highest-trust configuration in this system: a real, logged-in profile driven on a timer. Keep the trigger interval coarse (the CLI rejects intervals under 60 seconds), keep the workflow's `policy.requiredOrigins` narrow, and read `chrome-bridge audit summary` after the first few unattended runs.
- **Workflow files are inputs, not trusted code.** `schedule workflow` validates the file contract (`{version, name, steps: [{action, payload?, wait?}], policy: {requiredOrigins?}}`) and rejects anything malformed before writing an entry, but a workflow is only as trustworthy as whoever recorded it. Treat a workflow file received from elsewhere the way you would treat a script: read it first.

## Windows and cross-browser registration

Registering the host with another browser widens who can reach your real profile. The rules below are enforced by the installers and checked statically by `verify_install_contract.py`.

- **User scope only on Windows.** `setup-windows.ps1` writes exactly `HKCU:\Software\Google\Chrome\NativeMessagingHosts\com.automation.bridge` and, with `-Browser Edge|Both`, the matching `HKCU:\Software\Microsoft\Edge\...` key. It never writes `HKLM` and never asks for elevation. An `HKLM` registration would register the bridge for **every account on the machine**, so any other local user could drive your Chrome profile through it. If you find an `HKLM` bridge key, delete it.
- **The .cmd launcher is a local capability.** `bridge-host-launch.cmd` embeds the absolute token, policy, and log paths and starts the host. It is git-ignored, machine-specific, and must never be committed, shared, or copied into a synced folder. Anything that can execute it can start a host bound to your token files.
- **Windows file permissions are not implicit.** The installer breaks ACL inheritance and grants the current user only on `bridge_token.txt`, `bridge_tokens.txt`, and `bridge_policy.json`; POSIX `0600` has no Windows equivalent. If `icacls` warns, fix the ACL by hand before using the bridge - a token readable by other local accounts is a compromised token.
- **Existing secrets are never overwritten.** Re-running the installer keeps an existing token, token registry, and policy, and no token value is ever printed; stdout carries only manifest path, host name, host kind, port, and extension ID.
- **One extension at a time, across browsers.** Chrome and Edge registrations point at the same host and the same port. Two enabled bridge extensions - in one browser or in two - race for that port, and the loser fails closed.
- **Registration authorizes exactly one extension ID.** The Edge and Windows manifests carry a single `chrome-extension://<id>/` origin. If the browser assigns a different ID (a different key, a re-pack, a store build), re-run the installer with that ID rather than widening the allowlist.
- **Firefox artifacts are inert.** `scripts/generate_browser_manifests.py` only writes files under the git-ignored `dist/`; it registers nothing, reads no token, key, or policy, and its staged extension directory is validated to contain exactly `manifest.json`, `background.js`, `wake.html`, and `wake.js` with no local artifact. Firefox has no `chrome.debugger`, so a Firefox build could not enforce or exercise the debugger-backed action surface the guardrail contract covers - treat the staged output as unreviewed material, not an installable bridge.

## Handoff telemetry blackout

While a `waitForHandoff` request is in flight through a native host, a human is typing a password, a 2FA code, or a payment detail into the real tab. For that whole window the host **denies observation actions before policy evaluation**, so no client can watch the handoff:

- Blacked-out actions, in three families. **One-shot observations:** `screenshot`, `extractText`, `getHTML`, `storageState`, `printToPDF`, `searchTabs`, `getCurrentState`, `extractStructured`, `scanPromptInjection`, and `observe` (an accessibility snapshot of the page the human is typing into is the same exposure class as a screenshot). **Collector reads:** `consoleMessages`, `networkRequests`, `interceptedRequests`, and `screencastFrames` - a collector that was already running before the handoff would otherwise hand back a buffer spanning it. **Collector starts:** `startMonitoring`, `startInterception`, and `startScreencast` - a collector opened mid-handoff would be readable the moment the blackout lifts. The `stopMonitoring`/`stopInterception`/`stopScreencast` verbs are deliberately *not* blocked, since stopping capture is never an exposure. All blacked-out actions are answered `{"success": false, "error": "handoff in progress", "blackout": true}` and audited with decision `handoff_blackout`. Nothing is forwarded to Chrome.
- A composite action cannot smuggle an observation past the gate. `batch` and `replayWorkflow` dispatch their steps inside the extension, so the host evaluates the blackout against every nested step and denies the whole outer request if any step is blacked out.
- The blackout applies to **every** client, including the one that started the handoff, and it outranks policy: an `allowedActions: ["*"]` policy does not lift it.
- Everything else passes normally: `ping`, `policyCheck`, `policyInfo`, lease verbs, the `waitFor*` family, and interaction actions are unaffected.
- Scope is per tab when the handoff payload carries a numeric `tabId`. **A handoff with no `tabId` is global**: the extension resolves the active tab, which the host cannot see, so the safer reading is that every tab is blacked out. Symmetrically, an observation request that omits `tabId` is denied by any live handoff, since it could land on the tab the human is using.
- The in-flight record is registered immediately before the forward and released on every exit path - normal response, extension error, or timeout - so a failed handoff can never leave a host permanently blind. Both hosts serve each TCP connection on its own thread, so the registry is shared state guarded by a mutex and covers concurrent client connections (a handoff on one connection blacks out observation on all others).
- A `dryRun` request for a blacked-out action reports `wouldForward: false` with `verdict.reason: "handoff in progress"` and `verdict.blackout: true`.
- **The extension also stops capturing.** A host blackout only refuses *reads*; anything already recording the tab would keep filling a buffer that becomes readable the moment the handoff ends. So immediately after resolving the target tab, and **before** the banner goes up, the extension scrubs that tab: buffered console entries, network records, and dialogs are dropped and monitoring is stopped, buffered intercepted requests are dropped and interception is stopped, and buffered screencast frames are dropped and `Page.stopScreencast` is sent. The in-memory buffers are cleared before any CDP round trip, so a tab that refuses the stop commands still retains nothing; the response reports which surfaces were scrubbed in `scrubbedCaptures`. After a handoff, `consoleMessages`, `networkRequests`, `interceptedRequests`, and `screencastFrames` report their surface as inactive rather than returning data captured while the human was acting - restart them explicitly if you still need them.
