# Security model

Chrome Bridge is a trusted-local real-profile handoff bridge. The host policy, audit log, redaction, and confirmation-token flow are the security boundary for all raw TCP, CLI, and MCP clients.

## Trusted-local security warning

This bridge controls your real Chrome profile. It can read page content, take screenshots, drive forms, download files, inspect cookies through redacted probes, attach Chrome's debugger, and run script/debugger actions when policy allows them. Install it only for trusted local automation on a machine you control. Keep `bridge_token.txt`, `bridge_tokens.txt`, `extension_key.pem`, `bridge_policy.json`, debug logs, audit logs, session trace artifacts (`bridge_traces/`), recorded workflows (`bridge_workflow_last.json` and any workflow file you save), and the selector cache (`bridge_action_cache.json`) private and git-ignored.

The example policy is conservative: built-in defaults allow only `ping`, policy inspection, and lease actions until a local policy opts into more. Some README examples and live gates need explicit action/origin grants for the sites you intend to automate.

## Security notes

- TCP API is localhost-only and requires the shared token.
- Payload bodies such as cookies and DOM are not logged by the host.
- Host policy in `bridge_policy.json` (`BRIDGE_POLICY_FILE`) is the enforcement layer for every raw TCP/CLI/MCP client: the TCP API is localhost-only and token-gated, but token holders bypass MCP scoping, so deny/allow/confirmation rules are enforced in the native host before any action reaches the extension.
- MCP `readonly`/`allow_sensitive` controls are usability scoping, not the security boundary, because a client with the token can call the raw TCP API directly. Use `bridge_policy.json` for real restrictions; use `browser_policy_check` (or `test_client.py policyCheck`) to see what the host would decide.
- Built-in host defaults are fail-closed when no valid `bridge_policy.json` exists: only `ping`, `policyCheck`, `policyInfo`, and lease actions are allowed. `setup.sh` copies `bridge_policy.example.json` to make normal local automation an explicit opt-in. `policyInfo` is additionally answered host-side before the action gate (like `policyCheck`), so a client can always discover the active policy/audit file paths even under a deny-all policy; it returns only those paths, never policy contents.
- An org can distribute the policy itself as a **content-addressed bundle** (`policyBundle`): the host applies the bundle only when its SHA-256 matches the digest pinned in a lockfile, fails closed to the built-in default on any mismatch or read/parse error, re-verifies on reload, and composes every authority-bearing key so that a local layer can only tighten it - it can never drop a denied action or origin, a confirmation requirement, a `redactPatterns` regex, or a `secretMaskFile` dictionary the other side required. See "Org policy bundles: verified, content-addressed baselines" below.
- Actions listed in `requireConfirmation` return an opaque `confirmationToken` plus `resumeCommand`. `chrome-bridge confirm <token>` / MCP `browser_confirm` asks the host to recover the exact short-lived client identity, action, and payload; this intentionally allows an authenticated CLI client to approve a token produced by MCP. The older `browser_confirm_action` resend form remains available. Both paths re-run the original client's policy, live-origin, lease, and fingerprint checks before the host forwards anything, and tokens are one-use. Treat the opaque token as a short-lived local capability: this confirmation is friction against accidental use by a trusted token holder, not protection from a compromised bridge client or leaked token.
- Site policy (`allowedOrigins`/`deniedOrigins`) applies to tab-scoped actions too, not just URL-carrying ones. For an action whose payload has no URL/domain (e.g. `click`, `type`, `executeScript`, `getHTML` on a `tabId`), the host resolves that tab's live origin through a reserved internal lookup and evaluates policy against it before forwarding. When policy constrains origins and the origin cannot be resolved, the action is denied (fail-closed). `policyCheck` cannot see the live origin without forwarding, so its result includes `originDependent: true` for such actions to flag that the real request is additionally origin-checked.
- Egress policy (`egressAllowlist`) is a separate, narrower control: `allowedOrigins`/`deniedOrigins` govern **which page an action may act upon**, while `egressAllowlist` bounds **where the agent may make the browser send a new outbound request**. It is a list of host patterns using the same syntax and the same layered list merge as the origin lists, empty or absent means unconstrained, and it is enforced host-side before anything is forwarded. See "Egress allowlist: where the agent may send traffic" below for the covered actions, the precedence rules, and the traffic it deliberately cannot see.
- Audit export (`auditExport`) forwards audit events to a SIEM. It is a **mirror, not a new source**: the host writes the local audit log first, then re-encodes that exact already-masked event for the sink, so nothing can reach a collector that `bridge_audit.jsonl` does not already hold - no payload body, no response body, no cookie, no storage value, and no `secretMaskFile` value. The local append is synchronous and authoritative; the mirror is **asynchronous and best-effort**, so events still queued when the host stops are lost from the sink and only from the sink. Formats are `jsonl`, RFC 5424 `syslog`, and ArcSight `cef`. A malformed control block or a sink that refuses a write disables that sink for the life of the process after exactly one `audit_export_unavailable` event, and never blocks automation. See "Audit export: what leaves the machine" below for the field mapping tables.
- Python host only: set `BRIDGE_POLICY_APPROVAL_MODE=gui` (default on macOS) to show a native prompt when an otherwise-allowed action is blocked only because the target origin is not in `allowedOrigins`. The prompt offers `Deny`, `Allow This Time`, and `Always Allow`. `Allow This Time` creates a TTL-bound one-shot in-memory origin grant for the exact client/action/payload/target; `Always Allow` adds that origin to the local `bridge_policy.json`. Origin approval only authorizes the site, then the host re-runs normal policy evaluation, so actions in `requireConfirmation` still require a confirmation token. Set `BRIDGE_POLICY_APPROVAL_MODE=off` to disable prompts, or `BRIDGE_POLICY_APPROVAL_MODE=command` with `BRIDGE_POLICY_APPROVAL_COMMAND` for tests/custom frontends. Rust host users currently get the conservative deny/doctor flow without this GUI approval UX.
- Per-site permission modes (`siteModes`) attach a mode to an origin pattern instead of an action: `manual`, `auto` (the default when no pattern matches), or `skip`. They are merged **per pattern** across the `default` and `clients.<name>` layers, so a client layer overriding one origin inherits every other origin's mode. A mode only moves the confirmation gate, never the action or origin gates: a `deniedActions` or `deniedOrigins` match still denies, and `skip` only relaxes actions the policy already allows. `manual` requires a confirmation token for every mutating or high-risk action on a matching origin even when nothing is listed in `requireConfirmation`. `skip` pre-approves the confirmation gate for a matching origin, so no token is minted at all - and the waiver is written to the audit log as decision `confirmation_waived` with reason `siteMode skip`, because under an unattended pre-approval that log entry is the only trace a human later sees. When two patterns match, the longest pattern wins (a length tie is broken by the lexicographically smaller pattern) in both hosts, and a value outside `manual|auto|skip` is ignored rather than guessed at. `policyCheck`, `policyCheck --plan`, and every `dryRun` verdict report the resolved `siteMode` (null when no origin is known yet or no pattern matches). Edit modes with `chrome-bridge policy site-mode <originPattern> manual|auto|skip [client]` and `chrome-bridge policy clear-site-mode <originPattern> [client]`; MCP deliberately exposes no policy-mutation tool.
- `skip` can **never** waive these non-skippable confirmations, in either host: `executeScript`, `executeScriptCDP`, `getCookies`, `storageState`, `setCookie`, `deleteCookie`, `setStorageItem`, `removeStorageItem`, `clearStorage`, `startScreencast`, `clickAt`. They execute arbitrary script, read or rewrite real profile credentials and storage, start continuous capture of a logged-in profile, or click with no auditable element identity. An origin-level pre-approval is a statement about a *site*, not about those capabilities, so they keep requiring a per-call token no matter what `siteModes` says.
- **Read-only versus state-changing is computed from the payload, not the action name.** Both hosts resolve an `effectiveTier` of `read_only` or `mutating` for every request through `effective_action_tier(action, payload)`, and that tier - not the action name - is what `manual` gates. Three rules, in order: a `batch` or `replayWorkflow` is the **union over its steps**, so it is `read_only` only when every step is and any single mutating step makes the whole composite mutating (steps are extracted with the same `tabId` defaulting/retargeting the extension applies); a nominally read-only action **escalates** to `mutating` when its payload carries a state-changing flag from the table below; otherwise the tier is the action's own classification (`MUTATING_ACTIONS`, `DESTRUCTIVE_ACTIONS`, and the non-skippable set above are all `mutating`). Because `batch` is origin-exempt for site policy, the `manual` gate resolves a batch's mode from the union of its steps' live origins, so hoisting mutating actions into a batch cannot dodge a manual origin. `skip` additionally can never waive a confirmation for an escalated call: an origin-level pre-approval is a statement about a site, not about a flag the caller chose. The resolved tier is reported as `effectiveTier` in every `policyCheck` verdict (single and per plan step) and in every dry-run verdict, so a client can price a specific payload before sending it.
- The full escalation table, identical in `bridge.py` (`ESCALATING_PAYLOAD_FLAGS`) and `host-rs/src/main.rs`:

  | Action | Flag | Escalates when | Why it changes state |
  | --- | --- | --- | --- |
  | `screencastFrames` | `consume` | anything but literal `false` (the extension reads `consume !== false`, so an omitted flag escalates) | drains the tab's buffered frames irrecoverably; a second read cannot recover them |
  | `cacheSelectors` | `op` | `clear` or `import` (`list`/`export`, including the default, do not) | `clear` wipes the semantic-selector cache; `import` merges caller-supplied entries into it |
  | `resolveCachedSelector` | `cache` | a non-empty array | the extension merges those caller-supplied entries into the live selector cache before resolving |

  Actions audited and found clean, i.e. read-only for every payload they accept: `consoleMessages` (`resolveSourceMaps` copies the buffer first and releases its debugger context, so it never drains or rewrites collector state), `networkRequests` and `interceptedRequests` (copy-only reads with no flags), `observe` (`compact`/`roles`/`name`/`limit` are filters; its ref-registry write is unconditional, not caller-selected), `getCurrentState` (takes only a `tabId`), and `searchTabs` (`query`/`isRegex`/`caseSensitive`/`maxMatchesPerTab` only bound the search). MCP tool annotations stay statically conservative because an annotation cannot vary per call - `browser_batch` and `browser_screencast_save` are annotated mutating - and the host-side tier is the authoritative one.
- GitHub attachment helpers (`githubAttachUploadedFiles`, `githubSubmitComment`, `githubAttachPrBody`) are narrow tab-scoped actions. They remain subject to host origin policy and reject any tab whose URL origin is not `https://github.com`; the PR-body helper additionally requires a `/owner/repo/pull/number` path and exact scoped editor/save controls. They do not require broad `executeScript*` allowlisting.
- Audit logs are JSONL at `BRIDGE_AUDIT_LOG_FILE` / `bridge_audit.jsonl`, one event per request with `ts`, `client`, `action`, `targets`, `decision`, `reason`, `requestId`. They intentionally omit payload and response bodies.
- Session trace artifacts are opt-in and local: set the policy key `traceDir` (default `null`) and both hosts append exactly one JSONL event per trace-eligible request to `<traceDir>/<traceId>.jsonl`, after the request is fully processed - allow, host denial, extension error, or timeout alike. An event carries `ts`, `client`, `action`, `decision`, `reason`, `requestId`, `durationMs`, `targets` (tab ids only, never URLs or titles), `traceId`, `responseHash`, an optional `snapshotHash`, and `success`. It never carries a payload body, a response body, or a token: content is represented only as a SHA-256 of the canonical redacted response, and secret masking is applied before hashing so a known credential cannot be a hash preimage. The trace id comes from the caller (`traceId`/`sessionId`/`taskSessionId`) or the response's `sessionId`, and the file name is sanitized to `[A-Za-z0-9._-]` and capped at 80 characters, so a caller-supplied id cannot escape `traceDir`. Traces are still sensitive browsing metadata - which sessions ran, which tabs, when, and what was denied - so keep `bridge_traces/` private and git-ignored, exactly like the audit log. Read them with `chrome-bridge trace summary|tail` or MCP `browser_trace_summary`/`browser_trace_tail`.
- OpenTelemetry spans are opt-in **process** configuration, not policy, and off by default: with `BRIDGE_OTEL_ENABLED` unset the path is inert in both hosts (no import, no file, no socket) and request handling is identical to a host with no telemetry code. There is deliberately no policy key, so tracing can never be switched on for one client and can never change a policy decision. When enabled, a span carries only host-side metadata - action, resolved client name, decision, `effectiveTier`, duration, a **count** of touched tab ids, success, the host's request id, the session trace id, and `bridge.host`. It carries **no** payload or any field of one (no selectors, no URLs, no typed text), no response body, no page content or snapshot, no cookies, no storage values, no bridge or confirmation tokens, and no credential values; denial reasons and extension error strings are excluded too, since those can quote caller- or page-supplied text. The only attribute value not generated by the host is the caller's own trace/session id, and every string attribute is passed through the same `secretMaskFile` masking as the audit log before export. Nothing leaves the machine unless `BRIDGE_OTEL_ENDPOINT` is set; `BRIDGE_OTEL_FILE` is a purely local sink. Export is best effort on a background thread and a failing sink is logged once and disabled, so telemetry can neither delay nor fail a browser request. An inbound `traceparent` (TCP envelope field, MCP HTTP header, or CLI `--traceparent`) is host-only and stripped before forwarding, exactly like the token and `dryRun`. See `docs/telemetry.md`.
- Cookie and storage-state redaction is enabled by default through policy (`redact`): cookie values and sensitive storage keys are replaced with `<redacted>` before responses reach the client. Page-derived content from `getHTML`, `extractText`, `executeScript`, and `executeScriptCDP` is additionally masked against the client policy's `redactPatterns` (a list of regexes; use inline flags like `(?i)` for case-insensitivity) before it reaches the client.
- Secret masking is an additional, exact-match layer: set the policy key `secretMaskFile` to the path of a local `name=value` file (one pair per line, `#` comments allowed, mode `600` expected; see `bridge_secrets.txt.example`). Both hosts load it at policy load time, cache it by mtime, and replace every exact occurrence of each value with `<masked:name>` in every outbound response string (recursively, including nested objects and arrays) and in every audit-log field. Unlike `redactPatterns`, masking is independent of the `redact` toggle: these are known credentials and must never leave the host. A missing or unreadable file disables masking for that path after a single warning (logged and written to the audit log as `secret_mask_unavailable`); under a verified bundle the key can hold several paths, and one unreadable path never disables the others. `bridge_secrets.txt` is gitignored; never commit real values.
- Request-level `"dryRun": true` (CLI `--dry-run`, MCP `browser_action` payload) makes the host evaluate a request - token, policy, lease, origin dependency, confirmation requirement - and answer `{success, dryRun, wouldForward, action, targets, verdict}` without forwarding anything to Chrome. It is deliberately side-effect free: it never acquires or resumes a lease, never mints or consumes a confirmation token, never triggers the origin-approval prompt, and never performs the internal live-origin lookup. Host-side actions (`lease`, `release`, `leaseStatus`, `policyCheck`, `policyInfo`, `confirm`) report `wouldForward: false` because they never reach Chrome. `policyCheck` additionally accepts `{"plan": [...]}` (max 50 steps) to preflight a whole plan in one host-side call.
- The Python and Rust native hosts enforce the same baseline policy, audit, and redaction rules; this parity is covered by the guardrails contract (`verify_guardrails_contract.py`). Python's optional origin-approval prompt is an extra UX layer that can persist a local policy grant before the baseline policy is re-evaluated.
- `executeScript` uses `chrome.scripting` in the page MAIN world and can be blocked by strict page CSP. `extractText`, `getHTML`, `waitForText`, and handoff body checks also use normal extension page access, so they do not open Chrome's debugger notice.
- `executeScriptCDP`, compact and full accessibility snapshots, browser interactions, selector waits, screenshots, viewport control, emulation, monitoring, interception, geolocation, and performance metrics use `chrome.debugger`. On task-owned tabs, nearby debugger-backed actions share one connection that closes after 30 idle seconds. Chrome's debugger notice is browser-wide; placing a tab in a group does not contain or hide it. Chrome 118 or newer is required so this idle timer remains reliable when the extension worker is inactive.
- `downloads`, `contentSettings`, `history`, `bookmarks`, `host_permissions: <all_urls>`, cookie access, debugger access, and script execution are powerful. Use this profile for trusted automation only.
- `sessionStatus` reports cookie names and counts only, never cookie values; `waitForHandoff` only focuses a tab, marks its task group as needing review, shows a compact card, and waits - neither reads, imports, nor overwrites cookies. `credentialHandoff` narrows that to one field and is the supported way to enter a secret; see "Credential handoff: the intended way to enter a secret" below. Operating on the real profile is the bridge's design, not a leak, but `sessionStatus` output (which sites/accounts are logged in) is itself sensitive - keep it out of transcripts.
- Cookie and web-storage write ops (`setCookie`, `deleteCookie`, `setStorageItem`, `removeStorageItem`, `clearStorage`) are in the example policy's `requireConfirmation`, so each first call returns a one-use `confirmationToken` plus `resumeCommand` instead of mutating anything. They never log or echo the written value: the host omits payload bodies from the audit log, and the extension responses carry identifiers only - cookie name and domain for `setCookie`, the removed name for `deleteCookie`, scope and key for the storage item ops, and removed key counts for `clearStorage`. `deleteCookie` and `clearStorage` are destructive: they can sign the real profile out of a site or discard site state the human depends on.
- `searchHistory` and `searchBookmarks` read the real profile's private browsing record and are confirmation-gated in the example policy. `searchTabs` injects a bounded text match into every open `http`/`https` tab and returns origin hosts (never full URLs) plus capped snippets; snippets are page content, so treat all three outputs as sensitive and keep them out of transcripts. Because a single `searchTabs` call can return content from tabs the agent was never pointed at, MCP gates `browser_search_tabs` behind `BRIDGE_MCP_ALLOW_SENSITIVE=1` alongside history and bookmarks. Tabs that cannot be scripted are skipped and only counted.
- `startScreencast` is confirmation-gated in the example policy because it begins **continuous** capture of a real, logged-in profile: for as long as it runs, every pixel the tab renders is buffered, which is a far larger exposure than a single `screenshot`. `screencastFrames` returns base64 image data and must be drained through `chrome-bridge screencastSave` / MCP `browser_screencast_save`, which write the frames to a local directory and return only counts, byte totals, and paths - never frame data. Draining is irrecoverable, so both saves create and validate the destination *before* consuming the buffer, and clear only a prior save's artifacts (`frame-*.png`, `frame-*.jpg`, `frames.json`, `screencast.mp4`) from it so a shorter later save cannot silently present an earlier recording's frames as its own. Because the save consumes the buffer and writes local files, MCP classifies `browser_screencast_save` as mutating, not read-only, and drops it under `BRIDGE_MCP_READONLY=1`. Frames buffer solely in the extension service worker (memory-only, so a worker restart ends the recording) with a hard bound of 600 frames or ~50MB, dropping and counting the oldest frames past either bound. `stopScreencast` discards whatever is still buffered.
- `consoleMessages` is raw-output-sensitive: console text and stack frames carry page data and script URLs. Its optional `resolveSourceMaps` mode (CLI `--source-maps`, MCP `browser_console_messages(resolve_source_maps=True)`) resolves generated frames to original build positions, and those `source` values can reveal a site's private source file names, directory layout, and developer paths - report resolved locations only when the user asked for them and keep them out of transcripts. Resolution reads a map only from the script's own origin or an inline `data:application/json` map and answers `sourceMapStatus: "crossOriginRefused"` otherwise, so no third-party origin is contacted. Script text and the map's `sourcesContent` are never retained or returned - the extension reads a script solely to find its `sourceMappingURL` comment - and the CLI additionally scrubs any source-text-shaped field before printing. Parsed maps stay in extension service-worker memory, capped at 100 per-tab entries and dropped when the tab closes. It is not a new action name, so existing `consoleMessages` policy entries govern the source-map mode too.
- The bridge still intentionally lacks Playwright-style isolated browser contexts/profiles and multi-browser support; it controls the real Chrome profile. That ambient real-profile session is the point: it is what lets an agent reuse your existing logins and hand off to you for steps it should not do itself.
- The MCP HTTP transport reads a per-request bridge token from `Authorization: Bearer` or `X-Bridge-Token` (see `docs/mcp.md`). Those headers are bearer credentials for your real Chrome profile: keep the listener on `127.0.0.1`, never put it behind a shared or public reverse proxy, and never paste the header value into transcripts or logs. A request with no token header runs under the server's ambient `bridge_token.txt` identity, so an unauthenticated local caller reaching the endpoint gets that identity's policy scope - the port binding is the boundary.
- Private extension keys and store credentials must stay out of git. `extension_key.pem` (and any privately-held CRX packing key) is a local identity secret: it is git-ignored, it is never packaged, and `scripts/package_extension_store.py` neither creates nor reads it - the store upload zip contains only `manifest.json`, `background.js`, `wake.html`, and `wake.js`, and the script refuses to write a manifest carrying a `key` field. Store dashboard assets and metadata (publisher account details, screenshots of a logged-in real profile, review notes, OAuth client secrets or refresh tokens for any store API) are equally out of scope for this repository: no packaging path here uploads anything or contacts a Chrome Web Store API, so uploads stay a manual, human-performed step.
- Page content is untrusted input, not instruction. `extractStructured` narrows what a page can hand back to the fields a JSON Schema subset describes and never returns raw page text; `scanPromptInjection` reports a bounded heuristic `risk`/`matches` view of instruction-like page text (snippets capped at 160 characters, full text never returned), and `extractText`/`getHTML` can carry the same block as opt-in `injectionScan` metadata. Both are read-only observation actions and neither is a permission decision - see "Untrusted page content and prompt-injection posture" below.
- **A recorded workflow can reproduce mutating actions.** `startWorkflowRecording` and `replayWorkflow` are confirmation-gated in the example policy. Recording observes only what the bridge itself dispatched - never human clicks or keystrokes - so it can never capture more than the recording client was already allowed to do, and a failed action is never recorded. Replay is not a bypass: **before the outer `replayWorkflow` request is forwarded at all**, both native hosts walk `workflow.steps[]` - applying the same `tabId` retargeting the extension will apply, so a caller-supplied `tabId` is what gets origin-checked - and run each step through the full action, origin, `siteModes`, lease, and blackout pipeline. Any denied step denies the whole replay as `policy denied: workflow step <n>: <reason>`, and a reserved host-internal action is never dispatchable as a step. There is **no aggregate confirmation token**: a nested step that still requires confirmation after its own `siteModes` is applied fails the replay with `policy denied: workflow step <n> requires confirmation` and mints no token, because one outer approval cannot stand in for per-step approval and a half-run workflow has already mutated the page. Grant such a step explicitly through policy or a `skip` site mode instead. The extension then additionally refuses a step per step when the live tab origin is not in the workflow's `policy.requiredOrigins`. The exposure is the file: `bridge_workflow_last.json` and any `--out` path hold a replayable sequence of real mutations against a logged-in profile. They are git-ignored and written mode `600`; review a workflow before replaying one you did not record.
- Typed and stored values are redacted out of recordings by default. `type`/`fill` text, `setCookie`/`setStorageItem` values, `handleDialog` prompt text, and any credential-shaped payload key (`token`, `password`, `secret`, `credential`, `authorization`, `api_key`) are recorded as `<redacted>` with `requiresValue: true` and a `bindingKeys` entry, so a macro of a login never carries the password. Replay refuses the **entire** workflow - before running any step - until every redacted field is supplied through `bindings`/`--binding step<N>.<field>=<value>`, which keeps the secret in the caller's hands rather than on disk and prevents a partially-applied macro that stops at the credential field. `recordSensitive: true` (CLI `--record-sensitive`) opts one recording or one call out of that redaction and writes the literal value into the workflow file; use it only when you accept that file as a secret.
- **A postcondition is an assertion, not a read.** A version-2 workflow step may carry an `expect` clause, and `expect` is also a standalone action. It returns only `mode`, `negate`, `passed`, `attempts`, `elapsedMs`, and a short `reason` when it failed; the matched element, the matched text, the tab URL, and the extracted values never come back, so a failing assertion cannot be used to read a page an observation action is not allowed to read. `expect` changes nothing, so it appears in none of the mutating, sensitive, or destructive sets and stays on the read-only side of the classification. It is not exempt from the origin gate: both hosts enumerate a step's `expect` clause as a nested `expect` step during the same `replayWorkflow` recursion that polices the steps themselves, so a postcondition aimed at a tab the policy does not grant is denied with the rest of the replay rather than riding in unexamined. Retry is bounded by construction - `retry.max` clamps to `0..5` and `retry.delayMs` to `0..10000` - so an authored workflow cannot turn into an unbounded poll of a page that is never going to settle.
- The semantic-selector cache only self-heals **semantic** selectors (`text=`, `label=`, `role=`, `aria=`). A CSS selector is a literal address and is never cached or retargeted, so a stale CSS step fails instead of silently acting on a different element. A cached entry maps `(origin+pathname, semantic selector)` to a CSS path that resolved once, and a hit is trusted only when that path and the original semantic selector resolve to the **same live DOM node**: a path that still resolves but now addresses a replacement element is discarded just like one that stopped resolving, the semantic selector is re-resolved, and the step reports `selfHealed: true`. That closes the case where a page swaps a control and the old path keeps matching something - "still resolves" is not "still the right element". Entries imported from a cache file are rejected unless their selector is semantic and go through the same identity check at resolution time, so an edited `bridge_action_cache.json` cannot redirect a step onto a substituted element. The file is git-ignored and mode `600`: it holds no page content, but it does map a site's DOM structure.

## Egress allowlist: where the agent may send traffic

`egressAllowlist` answers a different question from the origin lists. `allowedOrigins`/`deniedOrigins` decide which page an action may operate on; `egressAllowlist` decides which hosts the agent may cause the browser to contact. Both are enforced in the native host before a request reaches the extension, and both use the same pattern syntax (`https://github.com`, `*://*.github.com`, ...) and the same list merge across the `default` and `clients.<name>` layers. Empty or absent means no egress constraint, so a policy that never sets it behaves exactly as before.

A violation is denied with the error `policy denied: egress not allowed` and a `policyDenial` companion whose `kind` is `egress`, whose `targets` name the destination that was refused, and whose `suggestedPatch` adds the pattern to the governing section's `egressAllowlist`. Grant one with `chrome-bridge policy allow-egress <pattern>` and remove one with `chrome-bridge policy clear-egress <pattern>`; MCP exposes no policy mutation, so egress is CLI-managed and `browser_policy_check` is how an MCP client sees the resulting denial.

**What it covers.** Exactly the actions whose payload names the destination, so the host can see it:

| Action | Destination the host reads | Why it is egress |
| --- | --- | --- |
| `navigate` | `payload.url` | drives the tab to that host |
| `navigateTaskSession` | `payload.url` | same, inside a task session's own tab |
| `downloadUrl` | `payload.url` | fetches that URL through the real profile |
| `setCookie` | `payload.url` | writes a cookie scoped to that host, which the browser then attaches to its next request there |

`batch` and `replayWorkflow` are not exempt: both hosts already walk their steps before forwarding the composite, so a nested `navigate` outside the allowlist denies the whole request as `batch step <n>: egress not allowed` / `workflow step <n>: egress not allowed`, with the index in `policyDenial.batchStep`. An egress-bearing action whose destination the host cannot resolve (missing or unparseable `url`) is denied rather than forwarded unchecked.

**Precedence.** Egress is evaluated alongside the target checks and never widens anything:

1. `deniedActions` wins. A denied action stays denied no matter what the egress allowlist says.
2. `allowedActions` wins. An action that is not allowed stays not allowed.
3. `deniedOrigins` then `allowedOrigins` win. A denied or non-allowed origin is still reported as `target denied` / `target not allowed`, even when the same host is on the egress allowlist. **Being on the egress allowlist never grants an origin that site policy denies.**
4. Only then is `egressAllowlist` applied.

`siteModes` and `requireConfirmation` are untouched: egress is a deny gate, so it never mints, waives, or consumes a confirmation token. `policyCheck` and `dryRun` gain no new fields; the denial simply surfaces as `verdict.reason: "egress not allowed"`, and a plan preview evaluates egress per step.

**What it cannot see, and therefore does not cover.** This is a real limitation, not an omission - do not read an egress allowlist as a claim that the browser can only talk to the listed hosts:

- **In-page navigation the agent triggers indirectly.** `click`, `press`, `type`, `fill`, and `drag` can follow a link or submit a form to any host. The destination lives in page markup the host never parses, so the host cannot know it. Such actions remain governed by site policy against the tab's live origin only.
- **Script-issued requests.** `executeScript` and `executeScriptCDP` can `fetch()` anywhere; the URL is inside the script body. These actions are confirmation-gated in the example policy precisely because they are unbounded.
- **Resource loads a page makes on its own.** Subresources, XHR, `fetch`, WebSockets, and beacons issued by a page the agent merely opened are the browser's normal behavior and are invisible to the host.
- **Uploads.** `uploadFile` and the `githubAttach*` helpers post to the tab's own origin, which site policy already governs, so they are not separately egress-checked.
- **`startInterception` in `fulfill` mode** fetches nothing: the extension answers from the inline `body`, so no new outbound request exists to bound. `continue` and `abort` likewise create no destination the host chooses.
- **`deleteCookie`** names a `url` but removes state and sends nothing.

The honest summary: `egressAllowlist` bounds the destinations an agent can name in a request, which is where an exfiltration attempt most often has to name a host. It does not and cannot bound every byte a real Chrome profile emits. Pair it with a narrow `allowedOrigins`, keep `executeScript*` confirmation-gated, and use the network layer (a proxy, DNS policy, or firewall) when you need an actual traffic boundary.

## DLP channels: what a mode actually enforces

`dlp` attaches a data-loss-prevention mode to a *channel* rather than to an action or an origin. It is enforced in the native host, before anything is forwarded to Chrome, and it is merged **per channel** across the `default` and `clients.<name>` layers, so a client layer can tighten one channel and inherit the rest.

```json
"dlp": {"upload": "audit", "download": "block", "screenShare": "audit"}
```

Three modes, identical in both hosts:

| Mode | Effect |
| --- | --- |
| `allow` | Default, and what an absent channel resolves to. Nothing is added; behavior is exactly as before. |
| `audit` | The action runs, and exactly one audit event with decision `dlp_audit` is written, naming the channel and nothing else. No file name, no file path, no frame data, no payload body. |
| `block` | The action is denied with reason `dlp blocked` and error `policy denied: dlp blocked`, carrying a `policyDenial` whose `kind` is `dlp` and whose `dlpChannel` names the channel. Nothing is forwarded. |

A mode outside those three (a typo) resolves to **`block`**, not to `allow`. A data-loss control that fails open because someone wrote `"blocked"` would be worse than no control, so the fail-closed direction is deliberate and differs from `siteModes`, where an unknown value is ignored.

The channels, and the exact chokepoints each one gates:

| Channel | Gated actions | Where enforcement lands |
| --- | --- | --- |
| `upload` | `uploadFile`, `githubAttachUploadedFiles`, `githubAttachPrBody` | The host refuses before forwarding, so CDP `DOM.setFileInputFiles` is never dispatched and the browser process never opens the file. The extension additionally refuses in `dispatchAction`, ahead of every handler, using the modes the host stamps on the forwarded envelope. |
| `download` | `downloadUrl` | The host refuses before forwarding, so `chrome.downloads.download` is never called. |
| `screenShare` | `startScreencast`, `screencastFrames` | The host refuses both the capture start and the frame read, so no frame is buffered and no buffered frame is drained. |
| `clipboard` | *(none)* | **Declared but not enforceable here.** See below. |

A gated action cannot be smuggled through a composite: `batch` and `replayWorkflow` steps are evaluated recursively, and a blocked step denies the whole request with `batch step <n>: dlp blocked` / `workflow step <n>: dlp blocked`. The `policyDenial` reports that step index in `batchStep` and names the smuggled step's own action, not the enclosing `batch`.

`policyCheck`, `browser_policy_check`, plan preflight steps, and dry-run verdicts all carry `dlp`: the resolved mode for that action's channel, or `null` when the action belongs to no channel.

### What DLP here cannot see

State this plainly rather than implying coverage:

- **`clipboard` has no bridge chokepoint.** No bridge action reads or writes the clipboard, and a copy or paste the *page* performs - `document.execCommand('copy')`, a `copy` event handler, the async Clipboard API, or a human pressing Cmd-C - never crosses the bridge at all. The channel is declared so that a policy can record the intent and so that a future clipboard action cannot be added without a mode already governing it, but setting `"clipboard": "block"` today **enforces nothing**. It is deliberately omitted from `bridge_policy.example.json` rather than listed as if it were covered.
- **Content, not just the channel, is out of scope.** A mode decides whether the channel may be used; it never inspects file contents, page text, or frame pixels. There is no classifier, no regex scan of an uploaded file, and no partial redaction of a transfer. `redactPatterns` and `secretMaskFile` govern what leaves the host in a *response*; they do not read an upload.
- **The `audit` event is metadata only.** It records the channel name so that a later review can see that a transfer happened on that channel. It deliberately does not record the file name, the path, the byte count, or the destination, because an audit log that quotes a path is itself a disclosure surface.
- **An upload's destination is still site policy's job.** An upload posts to the tab's own origin; `allowedOrigins`/`deniedOrigins` decide which origin that may be. DLP decides only whether the upload channel may be used at all.
- **Anything a page does on its own.** A page that exfiltrates by `fetch()` after the agent merely opened it is invisible to this control, as it is to `egressAllowlist`.

Modes are CLI-managed only, never through MCP: `chrome-bridge policy dlp <clipboard|upload|download|screenShare> allow|audit|block [client]`.

## Untrusted page content and prompt-injection posture

Everything the bridge reads out of a page - `extractText`, `getHTML`, `extractStructured`, `observe`, `searchTabs`, console text, intercepted bodies - is **data authored by whoever controls that page**. It is never instruction for the agent driving the browser, even when it is written as one, and even when it names the agent, its tools, or its operator.

- `scanPromptInjection` (CLI `chrome-bridge scanPromptInjection`, MCP `browser_scan_prompt_injection`, or `scanPromptInjection: true` on `extractText`/`getHTML`) flags instruction-like text by kind: instruction override, system-prompt disclosure, credential exfiltration, shell execution, policy tampering, operator concealment, permission coercion, tool redirection, and URL-borne data exfiltration. It returns `risk` (`low`/`medium`/`high`), `matches` with `kind`, `severity`, and a snippet capped at 160 characters, and `scannedChars`.
- The scanner is **heuristic** and deliberately small. It has false positives (a support page legitimately telling a human to click Allow) and false negatives (obfuscated, translated, encoded, or image-borne instructions). `risk: low` is not a clean bill of health.
- A scan result is **never an authorization decision**. It grants nothing and denies nothing: policy `allowedActions`/`deniedActions`, `requireConfirmation` gates, the origin allowlist, the cooperative lease, and the handoff blackout remain the only enforcement surface, and no risk value changes any of them. Do not read `risk: low` as permission to proceed, or `risk: high` as a substitute for a policy denial.
- `extractStructured` reduces exposure - only schema-described values cross the boundary, and the page text the extension read to find them stays in the extension - but those values are still page-authored. A `string` field can carry an injection attempt; schema validation constrains shape and type, not intent.
- Report page-derived findings as evidence, never execute them. A confirmation-gated action is confirmed by the human through `chrome-bridge confirm <token>`, never by text discovered on a page.

## Scheduled workflows and the no-human-present trust model

`chrome-bridge schedule workflow <workflowPath> --at <ISO8601>|--interval <seconds> [--name <name>]` writes **local metadata only**, into git-ignored `bridge_schedules.json` (mode `600`, or `BRIDGE_SCHEDULE_FILE`). Understand precisely what it is not:

- **It starts nothing.** Chrome Bridge ships no scheduler daemon, no timer thread, and no wake-up path for scheduled work. Registering a schedule does not make a workflow run - not once, not later, not in the background. Something outside the bridge (cron, launchd, systemd timers, a CI job, or a human) has to invoke the printed `runCommand`, and until it does, the entry is inert text on disk.
- **The registry is metadata, not a workflow.** An entry records the schedule name, the absolute workflow path, the trigger, the step count, the workflow's declared `policy.requiredOrigins`, the registration timestamp, and the run command. Step payloads are validated and then never copied into it, because a recorded step can carry typed text, search terms, or form values.
- **Registration is not authorization.** The host evaluates every replayed step at run time against the policy in force at that moment - `allowedActions`, `deniedActions`, the origin lists, `requireConfirmation`, `siteModes`, the lease, and the handoff blackout. A schedule cannot pre-authorize anything, and a workflow whose origins are not granted simply fails, one step at a time, in the audit log.
- **Unattended means no one is there to confirm.** A confirmation-gated step run with no human present blocks on a token nobody will approve, so an unattended workflow needs its origins explicitly granted and, where you accept the tradeoff, `siteModes: {"<origin>": "skip"}` for the specific site. That is a deliberate, auditable decision: `skip` still cannot waive the non-skippable set above, so no schedule can silently execute script, read cookies or storage state, write or delete cookies or web storage, start a screencast, or click by coordinate.
- **Prefer `manual` for anything you would not want to discover after the fact.** An origin left at `auto` with an empty `requireConfirmation` and a periodic trigger is the highest-trust configuration in this system: a real, logged-in profile driven on a timer. Keep the trigger interval coarse (the CLI rejects intervals under 60 seconds), keep the workflow's `policy.requiredOrigins` narrow, and read `chrome-bridge audit summary` after the first few unattended runs.
- **Workflow files are inputs, not trusted code.** `schedule workflow` validates the file contract (`{version, name, steps: [{action, payload?, wait?}], policy: {requiredOrigins?}}`) and rejects anything malformed before writing an entry, but a workflow is only as trustworthy as whoever recorded it. Treat a workflow file received from elsewhere the way you would treat a script: read it first.

## Windows and cross-browser registration

Registering the host with another browser widens who can reach your real profile. The rules below are enforced by the installers and checked statically by `verify_install_contract.py`.

- **User scope only on Windows.** `setup-windows.ps1` writes exactly `HKCU:\Software\Google\Chrome\NativeMessagingHosts\com.automation.bridge` and, with `-Browser Edge|Both`, the matching `HKCU:\Software\Microsoft\Edge\...` key. It never writes `HKLM` and never asks for elevation. An `HKLM` registration would register the bridge for **every account on the machine**, so any other local user could drive your Chrome profile through it. If you find an `HKLM` bridge key, delete it.
- **The .cmd launcher is a local capability.** `bridge-host-launch.cmd` embeds the absolute token, policy, and log paths and starts the host. It is git-ignored, machine-specific, and must never be committed, shared, or copied into a synced folder. Anything that can execute it can start a host bound to your token files.
- **Windows file permissions are not implicit.** The installer breaks ACL inheritance and grants the current user only on `bridge_token.txt`, `bridge_tokens.txt`, and `bridge_policy.json`; POSIX `0600` has no Windows equivalent. If `icacls` warns, fix the ACL by hand before using the bridge - a token readable by other local accounts is a compromised token.
- **Existing secrets are never overwritten.** Re-running the installer keeps an existing token, token registry, and policy, and no token value is ever printed; stdout carries only manifest path, host name, host kind, port, and extension ID.
- **One extension at a time, across browsers.** Chrome and Edge registrations point at the same host and the same port. Two enabled bridge extensions - in one browser or in two - race for that port, and the loser fails closed.
- **Registration authorizes exactly one extension ID.** The Edge and Windows manifests carry a single `chrome-extension://<id>/` origin. If the browser assigns a different ID (a different key, a re-pack, a store build), re-run the installer with that ID rather than widening the allowlist.
- **Firefox artifacts are inert.** `scripts/generate_browser_manifests.py` only writes files under the git-ignored `dist/`; it registers nothing, reads no token, key, or policy, and its staged extension directory is validated to contain exactly `manifest.json`, `background.js`, `wake.html`, and `wake.js` with no local artifact. Firefox has no `chrome.debugger`, so a Firefox build could not enforce or exercise the debugger-backed action surface the guardrail contract covers - treat the staged output as unreviewed material, not an installable bridge.

## Handoff telemetry blackout

While a `waitForHandoff` or `credentialHandoff` request is in flight through a native host, a human is typing a password, a 2FA code, or a payment detail into the real tab. For that whole window the host **denies observation actions before policy evaluation**, so no client can watch the handoff:

- Blacked-out actions, in three families. **One-shot observations:** `screenshot`, `extractText`, `getHTML`, `storageState`, `printToPDF`, `searchTabs`, `getCurrentState`, `extractStructured`, `scanPromptInjection`, and `observe` (an accessibility snapshot of the page the human is typing into is the same exposure class as a screenshot). **Collector reads:** `consoleMessages`, `networkRequests`, `interceptedRequests`, and `screencastFrames` - a collector that was already running before the handoff would otherwise hand back a buffer spanning it. **Collector starts:** `startMonitoring`, `startInterception`, and `startScreencast` - a collector opened mid-handoff would be readable the moment the blackout lifts. The `stopMonitoring`/`stopInterception`/`stopScreencast` verbs are deliberately *not* blocked, since stopping capture is never an exposure. All blacked-out actions are answered `{"success": false, "error": "handoff in progress", "blackout": true}` and audited with decision `handoff_blackout`. Nothing is forwarded to Chrome.
- A composite action cannot smuggle an observation past the gate. `batch` and `replayWorkflow` dispatch their steps inside the extension, so the host evaluates the blackout against every nested step and denies the whole outer request if any step is blacked out.
- **A handoff is a top-level action only.** The reverse case - a handoff *inside* a composite - is refused outright: a `batch` or `replayWorkflow` whose steps include `waitForHandoff` or `credentialHandoff` is denied before policy evaluation with `batch step <n>: handoff not allowed in a composite` / `workflow step <n>: handoff not allowed in a composite`, the index in `policyDenial.batchStep`, and nothing forwarded. The reason is that such a handoff could not be given a meaningful blackout at all. The composite's remaining steps are dispatched inside the extension and never pass back through the host, so a `batch: [credentialHandoff, screenshot]` would wait for the human to type the credential and then capture the tab from inside the same forwarded request, with no gate in between and no blackout that could have covered it. Refusing the shape is the only fail-closed answer; run the handoff as its own request, then continue. The same step extractors used for policy, DLP, and tier decisions do the walking, so nesting a composite inside a composite does not evade it.
- The blackout applies to **every** client, including the one that started the handoff, and it outranks policy: an `allowedActions: ["*"]` policy does not lift it.
- Everything else passes normally: `ping`, `policyCheck`, `policyInfo`, lease verbs, the `waitFor*` family, and interaction actions are unaffected.
- Scope is per tab when the handoff payload carries a numeric `tabId`. **A handoff with no `tabId` is global**: the extension resolves the active tab, which the host cannot see, so the safer reading is that every tab is blacked out. Symmetrically, an observation request that omits `tabId` is denied by any live handoff, since it could land on the tab the human is using.
- The in-flight record is registered immediately before the forward and released on every exit path - normal response, extension error, or timeout - so a failed handoff can never leave a host permanently blind. Both hosts serve each TCP connection on its own thread, so the registry is shared state guarded by a mutex and covers concurrent client connections (a handoff on one connection blacks out observation on all others).
- A `dryRun` request for a blacked-out action reports `wouldForward: false` with `verdict.reason: "handoff in progress"` and `verdict.blackout: true`.
- **The extension also stops capturing.** A host blackout only refuses *reads*; anything already recording the tab would keep filling a buffer that becomes readable the moment the handoff ends. So immediately after resolving the target tab, and **before** the banner goes up, the extension scrubs that tab: buffered console entries, network records, and dialogs are dropped and monitoring is stopped, buffered intercepted requests are dropped and interception is stopped, and buffered screencast frames are dropped and `Page.stopScreencast` is sent. The in-memory buffers are cleared before any CDP round trip, so a tab that refuses the stop commands still retains nothing; the response reports which surfaces were scrubbed in `scrubbedCaptures`. After a handoff, `consoleMessages`, `networkRequests`, `interceptedRequests`, and `screencastFrames` report their surface as inactive rather than returning data captured while the human was acting - restart them explicitly if you still need them.

## Credential handoff: the intended way to enter a secret

`credentialHandoff` exists so no caller ever has a reason to put a secret in a payload. Use it for passwords, passphrases, recovery codes, and one-time codes.

- **The value never crosses the bridge, and neither does its length.** The agent supplies a `selector`, not a value. The extension focuses that field and then polls it through an injected check that returns only `{present, empty, submitted, focused}`. Nothing anywhere in the path reads, echoes, hashes, measures, or stores the field's `value`: not the response, not the audit log, not a trace event, not an error message. A character count is deliberately excluded too, because the length of a secret narrows a brute-force search. The response reports `filled: true` and nothing derived from the value.
- **Compare with `fill`.** Routing a secret through `fill` puts it in the CLI argv, in the request payload the host reads, and in whatever transcript the caller keeps. `credentialHandoff` removes all three exposures. This is why it is **not** in the example policy's `requireConfirmation`: gating the safe path would push callers back toward `fill`.
- **The same blackout applies.** `credentialHandoff` registers the identical in-flight handoff record as `waitForHandoff` in both hosts, with the same scoping (numeric `tabId` scopes to that tab; no `tabId` is global) and the same `handoff in progress` denial and `handoff_blackout` audit decision. The record is released in a `finally` on success, error, and timeout.
- **Captures are scrubbed first.** Buffers for the target tab are dropped and monitoring, interception, and screencast are stopped **before** the tab or the field is focused, so no collector window can span the credential entry.
- **Scope is one field.** `mode: "filled"` (default) resolves when the field goes from empty to non-empty and the length settles; `mode: "submitted"` resolves when the owning form submits or the page navigates. Frame-scoped selectors are rejected rather than silently widened. On every exit path the banner is hidden, the transient marker attribute the extension used to track the field is removed, and the prior task-session state is restored.

## Org policy bundles: verified, content-addressed baselines

A fleet needs one policy that an admin authors centrally and a machine cannot quietly edit into something weaker. `policyBundle` is that mechanism, and it is enforced in the native host, not in the extension or the CLI.

```json
{
  "policyBundle": {
    "path": "/etc/chrome-bridge/org-policy.json",
    "lockfile": "/etc/chrome-bridge/org-policy.lock"
  },
  "default": { "deniedOrigins": ["*://intranet.example"] }
}
```

The stanza lives at the root of the local `bridge_policy.json` (its `default` layer is also accepted). See `bridge_policy_bundle.example.json` and `bridge_policy_bundle.lock.example` for the shape of a bundle and its lockfile.

**Verification.** On every policy load the host reads the bundle, computes its SHA-256, and compares it against the `sha256` recorded in the lockfile. The bundle is parsed **after** the digest matches, so a document that is not pinned is never interpreted. Only a matching digest applies the bundle. The lockfile is the authorization: distributing a bundle is not enough, an admin must also pin its digest on the machine.

**Fail closed, always.** A digest mismatch, an unreadable bundle, an unreadable or malformed lockfile, a malformed bundle, or a malformed `policyBundle` stanza all produce the same outcome in both hosts: the host serves the **built-in fail-closed default policy** (`ping`, `policyCheck`, `policyInfo`, and the lease actions only). It does not fall back to the local file, and it never falls back to the last bundle that verified - a previously good bundle that is swapped or corrupted loses its authority immediately. The rejection is logged and written to the audit log once as decision `policy_bundle_rejected` with the reason (`policy bundle digest mismatch`, `policy bundle unreadable`, `policy bundle malformed`, `policy bundle lockfile unreadable`, `policy bundle lockfile malformed`, `policy bundle misconfigured`) plus `expectedDigest` and `actualDigest`.

**Precedence.** A verified bundle supplies the `default` and `clients` layers that the existing merge already consumes, so the full order is:

```
built-in fail-closed default -> bundle default -> local bridge_policy.json default
                             -> bundle clients.<name> -> local clients.<name>
```

The local file wins on top because a local operator must be able to **tighten** the org baseline (a stricter machine, a narrower client). It is deliberately not the other way around, and "the local file wins" is therefore not a plain override: the keys that carry allow/deny authority, or authority over what leaves the host, are **composed per key** so that the local layer can only ever tighten.

**A local layer can never loosen a verified bundle.** Composition is driven by one flat table in each host (`POLICY_BUNDLE_COMPOSITION` in `bridge.py`, mirrored field for field in `host-rs/src/main.rs`), and every rule in it is monotonic. The local floor for a layer is that layer's own value when it defines one, else the local `default` layer's value, so a client layer is composed against the floor that would actually apply to it.

| Key | Composed as |
| --- | --- |
| `allowedActions`, `allowedOrigins` | Explicit **intersection** of two pattern lists. Each entry is classified as the bare wildcard `*`, an exact literal (no `*`, `?`, or `[`), or a nontrivial glob, and exactly three cases compose: a bundle `*` means the bundle does not constrain the list so the local list stands (and a local `*` can never widen a constrained bundle list); a literal survives when the other side's patterns permit it as a **name**; two **identical** nontrivial globs compose to that glob. A bundle glob the local list does not restate is dropped, which only tightens. An empty allow list denies everything and is therefore the tight end, never "unconstrained". |
| `egressAllowlist` | The same intersection, except that empty means unconstrained for this key: an empty bundle list leaves the local list alone, and an empty local list keeps the bundle's rather than lifting the constraint. |
| `deniedActions`, `deniedOrigins`, `requireConfirmation`, `redactPatterns` | **Union.** More entries is tighter here - more denied patterns, more confirmation-gated actions, more response-masking regexes - so both sides can add, and a local `[]` can never erase the bundle's entries. |
| `dlp` | Per-channel **strictest** mode (`block` < `audit` < `allow`); an unrecognised mode composes as `block`, matching what enforcement already does with a typo. |
| `siteModes` | Per-pattern **strictest** mode (`manual` < `auto` < `skip`); an unrecognised mode composes as `auto`. |
| `redact`, `audit` | `true` is the tight value, so a bundle `true` wins and a local `false` cannot switch it off. |
| `secretMaskFile` | **Union of paths**, bundle first, deduplicated. One surviving path stays a plain string, so an existing single-path policy is unchanged; two distinct paths compose to a list and both files are loaded, their entries merged longest-value-first. |

**Two differing globs on one allow-list key are a rejected misconfiguration, not a silent merge.** The intersection above is deliberately limited to what is decidable: bare `*`, exact literals, and identical globs. A local nontrivial glob that the bundle does not restate, against a bundle list carrying a nontrivial glob of its own - for example a bundle `"allowedActions": ["foo*"]` under a local `["foo?"]` - has no intersection expressible as a pattern list. Guessing would either escalate the bundle or, worse, keep the broader side and silently discard the local narrowing. So both hosts fail closed on the existing bundle-rejection path instead: the bundle is refused, the **built-in fail-closed default policy** is served, and one `policy_bundle_rejected` audit event carries `policy bundle composition conflict: <key> bundle pattern "…" and local pattern "…" are different globs with no representable intersection`. Like a digest mismatch, it is audited once per change rather than once per request. To narrow a glob locally, restate the same glob or list exact literals.

So a bundle whose `clients.<name>` layer sets `"deniedOrigins": []` cannot drop `*://intranet.example` that the local `default` denied, and symmetrically a local layer that sets `"redactPatterns": []` or points `secretMaskFile` at its own file cannot drop the regexes or the secret dictionary the org required. **A local layer can add secrets and regexes; it can never remove the org's.** Keys outside the table (`traceDir`, `auditExport`, and the local root keys) carry no such authority and keep plain local-over-bundle precedence.

**Re-verified on reload.** The digest is not trusted for the life of the process. The host's mtime-based policy reload covers the local policy file, the bundle, and the lockfile, so swapping the bundle on disk is caught on the next request and reverts to the fail-closed default. Because the check is keyed to those mtimes, each rejection is audited once per change, not once per request.

**No contents leak.** `policyInfo` gains `policyBundle: {path, verified, digest}` with the digest truncated to 12 hex characters. That is metadata only, consistent with the existing rule that `policyInfo` returns paths and never policy bodies. `chrome-bridge policy bundle verify|lock|show` is likewise metadata only: it prints paths, digests, and match/mismatch, never bundle contents.

A bundle governs the same surface as any other policy: it cannot grant an action the built-in classification treats as non-skippable, and every other host control (confirmation, leases, redaction, audit, egress) continues to apply on top of whatever the bundle allows.

## Audit export: what leaves the machine

`auditExport` forwards the host's audit events to a SIEM. It exists because an enterprise cannot deploy an agentic browser whose only record lives on the endpoint, and it is deliberately the *narrowest* thing that satisfies that: an additional sink for events the local log already holds.

**Export never precedes or replaces the local write.** `write_audit_event` appends to `bridge_audit.jsonl` first, under the audit write lock. Only after that append returns is the same already-masked event object handed to the export queue, and the re-encode and the sink write happen later on the export worker thread, under a *separate* export lock so a slow collector can never delay the local append. If the local write fails, nothing is exported: there is no event to mirror.

**Export is asynchronous and best-effort; the local log is the record.** The request thread does no export I/O. It resolves the sink once, pairs the event with that resolved sink configuration, and hands the pair to a bounded in-memory queue drained by one background daemon worker. Three consequences are worth stating plainly rather than implying a stronger guarantee:

- **A queued event can be lost.** The worker is a detached daemon thread, so events still in the queue when the host process exits or is terminated never reach the sink. There is deliberately no shutdown flush: blocking host teardown on an unreachable collector would be a worse failure than an incomplete mirror.
- **A queued event can be dropped under pressure.** The queue is bounded (1024 events). When it is full the newest event is dropped and counted, with one debug-log line for the first drop.
- **A queued event is never rerouted.** The sink is resolved on the request thread and travels with the event, so a policy reload while events are queued cannot send an already-authorized event to a destination configured later, and cannot redirect it into a sink the operator only enabled afterwards. An event reaches the destination that was in force when it was produced, or it reaches nothing.

In every one of those cases `bridge_audit.jsonl` still holds the event. **Treat the local audit log as the authoritative, complete record and the export sink as a best-effort mirror of it.** When a collector must be complete, ship `bridge_audit.jsonl` itself, or backfill with `chrome-bridge audit export` (see below), which reads the local log and is not subject to the queue.

**Export invents no fields.** Both hosts read only `ts`, `client`, `action`, `targets`, `decision`, `reason`, and `requestId` - the fields the audit log already carries. There is no payload body, no response body, no page content, no cookie, no storage value, and no token in an audit event, so there is none in an export line. A `secretMaskFile` value is masked before the local write, and the export re-encodes that same masked object, so a secret cannot reach a collector even when a denial's own target quoted it.

### Configuration

`auditExport` is a map-valued policy key, merged **per key** across the `default` and `clients.<name>` layers, so a client layer can point one client at a different destination without restating the format. Null or absent disables export entirely.

| Key | Required | Meaning |
| --- | --- | --- |
| `format` | yes | `jsonl`, `syslog`, or `cef` |
| `destination` | yes | A local file path for `jsonl`/`cef`; `udp://host:port`, `tcp://host:port`, or a unix datagram socket path for `syslog` |
| `rotateBytes` | no | Positive integer. File destinations only: rotate to `<destination>.1` when the next line would exceed it |
| `retainDays` | no | Positive number. File destinations only: at rotation time, delete an existing `<destination>.1` older than this window before the new one replaces it |

Rotation is a single generation with no compression, performed under the export lock, so it is safe under the host's thread-per-connection model. Absent `rotateBytes` means the sink grows without bound; absent `retainDays` means a rotated generation is never pruned by age.

A rotating file sink is therefore a **bounded buffer, not a durable record**. Once the sink has rotated more than once, each new rotation replaces `<destination>.1` and the older generation is gone. That is deliberate: it keeps a local sink from filling the disk. The complete record is always `bridge_audit.jsonl`, which is never rotated by this mechanism, so treat the file sink as a tail for local inspection and use a streaming `syslog` destination (or ship `bridge_audit.jsonl` itself) when an off-host copy has to be complete.

### Fail closed, loudly, once

A malformed `auditExport` block (`format` outside the three names, an empty `destination`, a non-positive `rotateBytes`/`retainDays`, or a non-object stanza) **disables export for that policy layer**. It does not fall back to a looser sink or to a default destination. A sink that then refuses a write - unwritable path, missing directory, unreachable collector, unresolvable host - disables that sink for the life of the process.

Either way the host writes exactly one line to the debug log and exactly one audit event, with `action: "auditExport"`, `decision: "audit_export_unavailable"`, `targets: [<destination or layer>]`, and the failure as `reason`. It is once per sink, not once per request: a dead collector must not turn into an audit-log flood. Automation is never blocked and never retried against a dead sink, and re-arming a sink requires a host restart, so a collector that failed cannot silently resume mid-session.

### Format: `jsonl`

The audit event verbatim: compact JSON, keys sorted, one line per event, appended to the destination file. This is the same object the local log holds, so a `jsonl` sink and `bridge_audit.jsonl` are field-for-field identical.

### Format: `syslog` (RFC 5424)

```
<PRI>1 TIMESTAMP - chrome-bridge - MSGID [chromeBridge@0 ...]
```

| Element | Value |
| --- | --- |
| `PRI` | facility `local0` (16) * 8 + severity. `132` for the deny class, `134` otherwise |
| VERSION | `1` |
| TIMESTAMP | `ts` as RFC 3339 UTC with milliseconds (`2025-01-01T00:00:00.123Z`), or `-` when absent |
| HOSTNAME | always `-`. The machine name is not the agent's to publish |
| APP-NAME | `chrome-bridge` |
| PROCID | always `-` |
| MSGID | `action`, filtered to printable ASCII and capped at 32 characters, or `-` |
| SD-ID | `chromeBridge@0` |
| SD params | `client`, `action`, `decision`, `reason`, `requestId`, `targets`, always in that order |
| MSG | omitted. There is no free-text message to leak into |

`targets` is the target list joined with `,`. Any absent, null, or empty field renders as `-`. Param values are escaped per RFC 5424 6.3.3 (`\`, `"`, `]`). A `tcp://` destination uses RFC 6587 non-transparent framing: one LF-delimited message per event.

The severity split is by decision text: a decision containing `deny`, `blackout`, or `unavailable` is a **warning** (4); everything else is **informational** (6). That keeps denials, handoff blackouts, and a dead export sink above routine allows in a collector's default view.

### Format: `cef` (ArcSight)

```
CEF:0|ChromeBridge|NativeHost|1.0|<decision>|<action>|<severity>|<extension>
```

`1.0` is the audit-export **schema** version, not the product version: a receiver keys its field mapping off it. Severity is `7` for the deny class described above and `3` otherwise. Header fields escape `\` and `|`; extension values escape `\` and `=`, and newlines become `\n`.

| CEF key | Audit field |
| --- | --- |
| `rt` | `ts` (epoch milliseconds), or `-` |
| `suser` | `client` |
| `act` | `action` |
| `outcome` | `decision` |
| `externalId` | `requestId` |
| `reason` | `reason` |
| `cs1Label` | the literal `targets` |
| `cs1` | `targets` joined with `,` |

Keys are always emitted in that order, and an absent value renders as `-`, so a line's shape does not change with the event.

Both hosts are byte-compatible for all three formats: the Python and Rust encoders produce the same line for the same event. `bridge_audit_export.example` holds one fabricated sample line per format.

**Session traces are not forwarded.** `auditExport` covers the audit log only. Session trace artifacts stay local JSONL files under `traceDir`, and an exported OpenTelemetry span (`BRIDGE_OTEL_*`) remains a separate, independently configured sink. A trace event correlates with an exported audit event through `requestId`; nothing about a trace leaves the machine because `auditExport` is on.

### Backfill and testing a destination

`chrome-bridge audit export --format <fmt> --destination <dest> [--since ...] [--limit N]` re-encodes the **existing local audit log** to a destination, independent of policy. Use it to backfill a collector that was added late, or to prove a destination works before enabling `auditExport` in policy. `--dry-run` formats and counts without writing or connecting. It prints metadata only - counts, byte totals, destination, and the number of malformed lines skipped - never an exported line. The one-shot path deliberately performs no rotation and no pruning: the operator named that exact destination, and silently renaming their file would be a surprise.
